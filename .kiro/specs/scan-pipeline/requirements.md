# Requirements Document

## Introduction

This spec covers the scan pipeline of Gravekeeper. Given a public GitHub repository URL, the pipeline resolves the repository and commit, discovers manifests, parses the selected manifests, gathers health facts for every registry dependency from public sources, classifies each dependency, summarizes the repository, and returns one typed result through `POST /api/scan`.

The pipeline reuses `/core` UNCHANGED: `parseManifest`, `classify`, `summarize` and the types `Result`, `HealthFacts`, `RawHealthFacts`, `Dependency`, `ParseResult`, `Classification`, `AssessedDependency`, `RepoSummary`, `Severity`, `SourceKind` and `Ecosystem` (see `.kiro/specs/dependency-graveyard-core/requirements.md`). No requirement in this spec modifies `/core`.

The pipeline has four layers:

1. Network adapters in `/adapters`, one per upstream source, behind interfaces. They perform HTTP only.
2. Pure mapping functions in `/pipeline/mapping` that convert raw upstream JSON into `RawHealthFacts`. They never import `/adapters` and never read the clock.
3. An orchestrator in `/pipeline` that sequences discovery, lookups, mapping, `classify` and `summarize`, with timeouts, retries, concurrency limits, budgets and caches.
4. A thin Next.js App Router route handler at `/app/api/scan/route.ts`.

The upstream response shapes used here were verified by live HTTP requests on 2026-11-17 (PowerShell and the `gh` CLI). No fetch MCP server is configured in this environment, so the verification column of the Endpoint_Fact_Map says "Verified live (HTTP), not via MCP". Anything not in that list is marked "Not verified". A requirement never depends on a field that is not verified, except where it states a fallback to unknown.

This Next.js version has breaking changes (see `AGENTS.md`). The requirements stay framework-neutral. The design phase MUST read the relevant guide in `node_modules/next/dist/docs/` before specifying the route handler.

### Out of Scope

- UI: tombstones, ghosts, lanterns, components, layouts and pages.
- Resurrect: alternative suggestions and manifest patch generation.
- End-user authentication, accounts and login. The only credential is the server-side `GITHUB_TOKEN`.
- Private repositories and repositories the server token cannot read without special access.
- Lockfiles: `package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `poetry.lock`, `Pipfile.lock` and `Cargo.lock` are not read, not fetched and not used. The Pipeline never resolves a version from a lockfile. Manifest formats other than `package.json`, `requirements.txt` and `Cargo.toml` are also out of scope.
- Version range resolution (npm semver, PEP 440, Cargo semver ranges). Only exact pins are recognized (Requirement 7). Every other dependency is checked at the latest release (deps.dev default version). Full resolution is deferred (decided in session 9, Open Question 1).
- Health assessment of `git` and `path` dependencies. Core reports them as unassessed.
- Monorepo workspace expansion (following `workspaces`, `[workspace] members` or `-r` includes). Each manifest is scanned as listed.
- Changes to `/core`, including new rules, constants or types.
- Persistent storage. Caches are server-side, in memory, and lost on restart.
- Rendering of notes or statuses. The pipeline only produces data.

### Conventions

- Criteria tagged **[PBT]** are verified with fast-check in files named `<module>.property.test.ts`. Untagged criteria use example-based tests.
- Every criterion that names an upstream response field cites the Endpoint_Fact_Map row it relies on as `(EF-n)`.
- Every threshold, limit and size is a named constant listed in the Constants table. Criteria refer to constants by name.
- Environment variables are listed in the Environment_Variables table.
- Source code cites the requirement number in a comment above each rule (steering rule).

## Glossary

- **Pipeline**: The orchestrator in `/pipeline` that runs discovery, lookups, mapping, classification and summarization for one scan.
- **Scan_Route**: The route handler for `POST /api/scan` in `/app/api/scan/route.ts`.
- **Adapter**: A module in `/adapters` that performs HTTP requests to one upstream and returns raw JSON or text. An Adapter contains no mapping logic.
- **Source_Port**: The TypeScript interface an Adapter implements, named `<Name>Source` (for example `GithubSource`). The Source_Ports are declared in `/pipeline/ports`, not in `/core` (see Open Question 9).
- **Mapper**: A pure function in `/pipeline/mapping` that converts raw upstream JSON (type `unknown`) and an `asOf` value into part of a `RawHealthFacts`.
- **Mapper assembly function**: The pure function in `/pipeline/mapping` that combines the outputs of the Mappers for one Lookup_Target into one `RawHealthFacts` (Requirement 13, criterion 4).
- **Logger**: The injected component of Requirement 22, criterion 5 that writes log lines (Requirement 20, criterion 6).
- **Upstream_Source**: One of `github`, `depsdev`, `osv`, `npm`, `cratesio`, `pypi`. The `github` source covers the GitHub REST API, GitHub GraphQL API and GitHub raw content.
- **Source_Status**: One of `ok`, `partial`, `failed`, computed per Upstream_Source by Requirement 17.
- **Work_Unit**: One logical request to an Upstream_Source, including its retries and backoff waits (for example one package lookup, one batch or one advisory id). A Work_Unit ends as `ok` (a 2xx answer or a 404 answer meaning "absent") or `failed` (any other end, including skipped, cancelled and not started).
- **Scan_Deadline_Signal**: An abort signal tied to the scan deadline. The Pipeline aborts it when `SCAN_DEADLINE_MS` have elapsed since Scan_Start on the injected clock. Every outbound request, backoff wait and `Retry-After` wait of the scan, including the Discovery_Requests, is bound to it (Requirement 16).
- **Deadline_Cancelled_Unit**: A Work_Unit that had an attempt in flight, or was waiting between attempts, when the Scan_Deadline_Signal aborted, or that Requirement 15, criterion 6 or 8 ended early because a further wait would have ended after the scan deadline. It ends `failed` with reason category `deadline`.
- **Deadline_Unstarted_Unit**: An Applicable_Unit that had sent no attempt when the Scan_Deadline_Signal aborted (including one that waited for a concurrency slot). It ends `failed` with reason category `deadline`.
- **Applicable_Unit**: A Work_Unit the Pipeline needed in order to produce the requested facts. A lookup that is not needed (for example no GitHub source repository link exists) is not applicable.
- **Repo_Ref**: The record `{ host, owner, repo, branch }` produced by URL parsing. `branch` is a string or null.
- **Web_Host**: The only host accepted in repository URLs, derived by Requirement 2.
- **Canonical_Repo_URL**: The string `https://<Web_Host>/<owner>/<repo>` built from a Repo_Ref, with `/tree/<branch>` appended when `branch` is not null.
- **Commit_SHA**: The 40-character hexadecimal SHA of the head commit of the scanned branch (EF-13).
- **Manifest_Path**: A slash-separated repository-relative path to a manifest file, with no leading slash.
- **Manifest_Candidate**: The record `{ path, format, depth, sizeBytes }` for a discovered manifest, where `format` is a core `ManifestFormat`.
- **Root_Manifest**: A Manifest_Candidate whose `path` contains no `/`.
- **Skipped_Directories**: The list `DISCOVERY_SKIP_DIRS` of directory names that discovery never descends into.
- **Discovery_Result**: The record `{ candidates, truncatedTree, depthLimited, countLimited }` returned by discovery.
- **asOf**: One ISO 8601 UTC instant captured exactly once per scan by the Scan_Route (or Pipeline entry) and passed down as an argument. Mappers receive it as a parameter.
- **Day_Count**: `floor((asOf - date) / DAY_MS)` for a valid date, clamped to 0 when the date is after asOf (Requirement 6).
- **Lookup_Target**: The tuple (`ecosystem`, `name`) of a registry Dependency, after deduplicating across the selected manifests. One Lookup_Target is looked up once per scan.
- **Version_Basis**: One of `pinned` (an exact pin from the manifest, found in the upstream version list), `default` (the latest release, which is the deps.dev default version), or null when the Lookup_Target has no Selected_Version (Requirement 7, criteria 8, 9 and 11). It is recorded per Lookup_Target.
- **Selected_Version**: The version string that version-specific facts (deprecation, vulnerabilities) are computed for.
- **Exact_Pin**: A `versionSpec` that matches the Exact_Pin patterns in Requirement 7.
- **Source_Repo**: The `github.com/<owner>/<repo>` project that deps.dev links to a package version through `relatedProjects` with `relationType` `SOURCE_REPO` (EF-2).
- **Advisory**: An OSV vulnerability record fetched from the OSV vulnerability detail endpoint (EF-6).
- **Advisory_Score**: The `cvss3Score` of the deps.dev advisory record of one Advisory id (EF-25). It is valid only when it is a finite JSON number from 0.0 to 10.0 inclusive.
- **Counted_Advisory**: An Advisory that is not withdrawn (EF-8) and not informational (EF-10).
- **Alias_Group**: A set of advisory ids connected through `aliases` (EF-9). Each Alias_Group counts as one vulnerability.
- **GitHub_Budget**: The most recently observed `remaining` value of the GitHub rate limit, read from REST headers `x-ratelimit-remaining` (EF-16) or from GraphQL `rateLimit.remaining` (EF-18). GitHub_Budget is kept per scan and is unknown at Scan_Start (Requirement 14, criteria 1 and 6).
- **Scan_Note**: A record `{ code, message, details? }` in the `notes` list of a Scan_Result. `message` is built from a fixed template, never from raw upstream text.
- **Scan_Result**: The success body of `POST /api/scan` (Requirement 18).
- **Scan_Error**: The error body of `POST /api/scan`: `{ ok: false, error: { code, message, details? } }` (Requirement 21).
- **Upstream_Cache**: The server-side in-memory cache of upstream response bodies (Requirement 19).
- **Scan_Cache**: The server-side in-memory cache of complete Scan_Results (Requirement 19).
- **Fixture**: A recorded upstream response stored under `/tests/fixtures`.
- **Live_Tests_Flag**: The environment variable `GRAVEKEEPER_LIVE_TESTS`. Live contract tests run only when it equals `1`.
- **Token**: The value of `GITHUB_TOKEN`.
- **Secret_Sinks**: Every place a Token could leak: Scan_Result, Scan_Error, Scan_Route response bodies and response headers, Upstream_Cache entries, Scan_Cache entries, log lines, captured log output, error messages, thrown error messages and Fixtures.
- **URL_Parser**: The pure function that converts `repoUrl` text into a Repo_Ref or an `invalid-url` error, and its inverse formatter (Requirement 1).
- **Version_Selector**: The pure function that converts a `versionSpec` and an ecosystem into an Exact_Pin value or null (Requirement 7, criteria 1, 2 and 10).
- **PEP503_Normalization**: The PyPI name normalization of the core spec: ASCII lowercase, with every run of `-`, `_` and `.` collapsed to one `-`.
- **CVSS_Function**: The pure function that converts a CVSS 3.0 or 3.1 base vector string into a base score and a Severity (Requirement 10).
- **GraphQL_Alias**: The name `rN` of one `repository` selection in a GitHub GraphQL request, where N is the zero-based position of the Source_Repo within that one request (EF-17).
- **Attempt**: One HTTP request sent for a Work_Unit. A Work_Unit has between 1 and `RETRY_MAX_ATTEMPTS` Attempts.
- **Retry_Policy**: The pure rules of Requirement 15 that decide whether a further Attempt is made and how long to wait before it.
- **Concurrency_Limiter**: The component that keeps the number of Attempts in flight for one Upstream_Source at or below its `CONCURRENCY_*` constant (Requirement 15, criterion 3).
- **Injected_Clock**: A no-argument function that returns the current time as epoch milliseconds. The Pipeline, the Adapters and the caches read time only from it.
- **Scan_Start**: The Injected_Clock value read once when the Pipeline entry is called. `SCAN_DEADLINE_MS` and `SCAN_RESPONSE_MARGIN_MS` are measured from it.
- **GitHub_Request**: A REST or GraphQL request to the `github` Upstream_Source, excluding requests to `GITHUB_RAW_HOST`.
- **Discovery_Requests**: The repository request (EF-12), the branch request (EF-13) and the tree request (EF-14).
- **Reason_Category**: One of the nine values `timeout`, `network`, `rate-limited`, `http-error`, `budget`, `deadline`, `token-missing`, `prerequisite` and `truncated`, assigned to a Work_Unit that did not end `ok` (Requirement 15, criterion 15; Requirement 17, criteria 5, 9 and 13).
- **Architecture_Test**: The test of Requirement 22 that parses source text and reports import and API-use violations.
- **Fixture_Replay**: The test helper that serves recorded Fixtures in place of network responses (Requirement 23, criterion 3).
- **Fixture_Recorder**: The tool that calls the real upstreams and stores Fixtures, only when the Live_Tests_Flag equals `1` (Requirement 23, criteria 7 and 10).
- **Live_Contract_Test**: A test that calls a real upstream and checks the field paths of an Endpoint_Fact_Map row, only when the Live_Tests_Flag equals `1` (Requirement 23, criterion 8).
- **Verified_Row**: An Endpoint_Fact_Map row whose Verification column begins with "Verified live (HTTP), not via MCP".

## Requirements

### Requirement 1: Repository URL parsing

**User Story:** As a developer, I want to paste a GitHub repository URL in any common form, so that I do not have to reformat it.

#### Acceptance Criteria

1. WHEN `repoUrl`, after trimming leading and trailing whitespace characters (Unicode White_Space), has at most `REPO_URL_MAX_LENGTH` Unicode code points and has the form `[http://|https://][www.]<Web_Host>/<owner>/<repo>[.git][/]`, THE URL_Parser SHALL return a Repo_Ref with `host` equal to the Web_Host that Requirement 2 derived and that was passed to the URL_Parser as an argument, the given `owner`, the given `repo` with one trailing `.git` removed, and `branch` equal to null.
2. WHEN `repoUrl` has the form `[http://|https://][www.]<Web_Host>/<owner>/<repo>[.git]/tree/<branch>[/]`, with `tree` written in lowercase, THE URL_Parser SHALL return a Repo_Ref with `branch` equal to the text after `/tree/` (after removing one trailing `/`) with every `%XX` sequence decoded as UTF-8, which MAY contain `/` separators between non-empty segments, and SHALL NOT decode `+` to a space.
3. THE URL_Parser SHALL compare the scheme, the optional `www.` prefix and the host case-insensitively, SHALL compare `tree` and `.git` case-sensitively in lowercase, and SHALL keep `owner` and `repo` in the case written.
4. WHEN `repoUrl` has a `#fragment`, or a query string that is empty or in which every parameter name is listed in `URL_IGNORED_QUERY_PARAMS`, THE URL_Parser SHALL ignore the fragment and that query string, where a parameter name is the text before the first `=` of one `&`-separated item, compared case-sensitively, and parameter values are not inspected.
5. IF `repoUrl` has a host other than Web_Host (other than the optional `www.` prefix), THEN THE URL_Parser SHALL return the error `invalid-url` with `details.part` equal to `host` and a message, built from a fixed template, that contains Web_Host and does not contain the input.
6. IF `repoUrl` has path segments other than `/<owner>/<repo>` optionally followed by `/tree/<branch>` (for example `/issues`, `/blob/...`, `/pull/1`, `/Tree/main`, a missing repo, an empty path segment such as `//`, more than one trailing `/`, or nothing after `/tree/`), THEN THE URL_Parser SHALL return the error `invalid-url` with `details.part` equal to `path` and a message, built from a fixed template, that states the accepted forms.
7. IF, after trimming, `repoUrl` is empty, is longer than `REPO_URL_MAX_LENGTH` Unicode code points, contains a whitespace character or a control character (U+0000 to U+001F, U+007F), has a scheme other than `http` or `https`, has user information (an `@` in the authority), has an explicit port (a `:` in the authority), or has a query parameter whose name is not in `URL_IGNORED_QUERY_PARAMS` (including an empty name), THEN THE URL_Parser SHALL return the error `invalid-url` with `details.part` equal to `url`, where the authority is the text between the optional scheme and the first `/`, `?` or `#`.
8. IF `owner` is not 1 to `OWNER_MAX_LENGTH` ASCII letters, digits and single hyphens, or begins or ends with a hyphen, or contains two consecutive hyphens, THEN THE URL_Parser SHALL return the error `invalid-url` with `details.part` equal to `owner` and a message, built from a fixed template, that names the owner.
9. IF `repo`, after removing one trailing `.git`, is not 1 to `REPO_NAME_MAX_LENGTH` characters from ASCII letters, digits, `.`, `_` and `-`, or equals `.` or `..`, THEN THE URL_Parser SHALL return the error `invalid-url` with `details.part` equal to `repository` and a message, built from a fixed template, that names the repository.
10. IF the branch, after percent-decoding, is longer than `BRANCH_MAX_LENGTH` Unicode code points, contains an invalid percent-encoding (a `%` not followed by two hexadecimal digits, or a decoded byte sequence that is not valid UTF-8), contains a control character, space, `~`, `^`, `:`, `?`, `*`, `[`, `\`, `..`, `@{`, `//`, begins with `-` or `/`, or ends with `/`, `.` or `.lock`, THEN THE URL_Parser SHALL return the error `invalid-url` with `details.part` equal to `branch` and a message, built from a fixed template, that names the branch.
11. THE URL_Parser SHALL format a Repo_Ref as its Canonical_Repo_URL, with `https://` as the scheme, no `www.`, no `.git` and no trailing `/`, and with every character of the branch other than ASCII letters, digits, `-`, `.`, `_` and the `/` separator percent-encoded as UTF-8.
12. [PBT] THE URL_Parser SHALL satisfy, for every generated Repo_Ref with valid parts (`host` equal to Web_Host, `owner` valid under criterion 8, `repo` valid under criterion 9 and not ending in `.git`, `branch` null or valid under criterion 10), `parse(format(ref))` equal to `ref` (see Open Question 29).
13. [PBT] THE URL_Parser SHALL satisfy, for every generated accepted input string `s` whose parsed `repo` does not end in `.git`, `format(parse(format(parse(s))))` equal to `format(parse(s))` (normalization is idempotent; see Open Question 29).
14. [PBT] THE URL_Parser SHALL return, for every generated string input, either a Repo_Ref or an `invalid-url` error, and SHALL NOT throw.
15. [PBT] THE URL_Parser SHALL return, for every accepted input, equal Repo_Refs for the variants with and without `https://`, `http://`, `www.`, a trailing slash and `.git`, and for the variants that change only the case of the scheme and host.
16. IF more than one of criteria 5 to 10 applies to the same `repoUrl`, THEN THE URL_Parser SHALL return the error of the first applicable criterion in the order 7, 5, 6, 8, 9, 10.
17. [PBT] THE URL_Parser SHALL return the error `invalid-url`, for every generated accepted input to which exactly one of these mutations is applied: replacing the host with another host, adding an explicit port, adding user information, adding a query parameter whose name is not in `URL_IGNORED_QUERY_PARAMS`, or adding a path segment other than `tree` after `<repo>`.

### Requirement 2: GitHub host configuration

**User Story:** As an operator, I want the GitHub hosts to come from configuration, so that the Pipeline works with GitHub Enterprise Server.

#### Acceptance Criteria

1. WHEN a scan starts, THE Pipeline SHALL read the REST base URL from `GITHUB_API_URL` and the GraphQL URL from `GITHUB_GRAPHQL_URL` once, before the first GitHub request of that scan, using `GITHUB_DEFAULT_API_URL` and `GITHUB_DEFAULT_GRAPHQL_URL` when the variable is unset or is an empty string (zero characters, no trimming).
2. WHEN the API URL, after removing one trailing `/` and comparing scheme and host case-insensitively and path case-sensitively, equals `GITHUB_DEFAULT_API_URL`, THE Pipeline SHALL set Web_Host to `GITHUB_DEFAULT_WEB_HOST`.
3. WHEN the API URL, after removing one trailing `/`, has the scheme `https`, a host other than `GITHUB_DEFAULT_WEB_HOST`, no user information, no explicit port, no query and no fragment, and a path equal to `GHES_API_PATH_SUFFIX` (compared case-sensitively), THE Pipeline SHALL set Web_Host to the host of the API URL in lowercase (EF-24).
4. IF the API URL is not a parsable absolute URL, or matches neither criterion 2 nor criterion 3, THEN THE Pipeline SHALL return the error `internal-error` (HTTP 500, Requirement 21) with a fixed message that names the variable `GITHUB_API_URL` and does not include its value, and SHALL send no upstream request for that scan.
5. WHILE Web_Host is not `GITHUB_DEFAULT_WEB_HOST`, THE URL_Parser SHALL accept only Web_Host (with the optional `www.` prefix of Requirement 1) as the host of `repoUrl`, and SHALL return the error `invalid-url` (Requirement 1, criterion 5) for a `repoUrl` with the host `github.com`.
6. WHEN the github Adapter fetches manifest text (EF-15), THE github Adapter SHALL send the request to `GITHUB_RAW_HOST` for a Web_Host equal to `GITHUB_DEFAULT_WEB_HOST`, and otherwise to the blobs endpoint of the API URL using the `tree[].sha` of the manifest, and SHALL count the blobs requests against GitHub_Budget (Requirement 14).
7. THE Pipeline SHALL read the Token from `GITHUB_TOKEN` only in server-side modules, and SHALL treat the Token as unset when `GITHUB_TOKEN` is unset or an empty string (Requirement 20).
8. IF the host segment of a Source_Repo (the text before the first `/` of `projectKey.id`, compared case-insensitively) is not Web_Host, THEN THE Pipeline SHALL treat the Source_Repo as absent (EF-2) and Requirement 11, criterion 7 applies. Because every Source_Repo host is `github.com` (EF-2), every Source_Repo is absent when Web_Host is not `GITHUB_DEFAULT_WEB_HOST`.
9. IF the GraphQL URL is not a parsable absolute URL with the scheme `https`, THEN THE Pipeline SHALL return the error `internal-error` (HTTP 500, Requirement 21) with a fixed message that names the variable `GITHUB_GRAPHQL_URL` and does not include its value, and SHALL send no upstream request for that scan.
10. [PBT] THE Pipeline SHALL return, for every generated string pair used as `GITHUB_API_URL` and `GITHUB_GRAPHQL_URL` (including empty, unparsable and non-`https` values), either a configuration in which Web_Host is a lowercase host name with no scheme, port, path or user information, or an `internal-error` whose message does not contain either input string, and SHALL NOT throw.
11. WHEN more than one configuration error applies to one scan, THE Pipeline SHALL return the `internal-error` of the first applicable check in the order criterion 4, criterion 9, Requirement 20 criterion 11, and SHALL return a configuration error before any `invalid-url` error (Requirement 21, criterion 14(a)).

### Requirement 3: Repository and branch resolution

**User Story:** As a developer, I want the scan to be tied to one commit, so that results are reproducible and cacheable.

#### Acceptance Criteria

1. WHEN a Repo_Ref is parsed, THE Pipeline SHALL send the repository request (EF-12) for the `owner` and `repo` of the Repo_Ref as the first GitHub request of the scan, including when `branch` is not null.
2. IF the repository request returns HTTP 404, or the body has `private` equal to true (EF-12), THEN THE Pipeline SHALL return the error `repo-not-found` with a fixed-template message stating that the repository does not exist or is not public, and SHALL send no further GitHub request for this scan.
3. WHEN the Repo_Ref `branch` is null and `default_branch` is a non-empty string of at most `BRANCH_MAX_LENGTH` characters (EF-12), THE Pipeline SHALL select `default_branch` as the branch.
4. WHEN a branch is selected (the Repo_Ref `branch` when it is not null, otherwise `default_branch`), THE Pipeline SHALL request that branch name unchanged (EF-13) and SHALL set Commit_SHA to `commit.sha`.
5. IF the branch request returns HTTP 404, THEN THE Pipeline SHALL return the error `branch-not-found` with a fixed-template message naming the selected branch, and SHALL send no further GitHub request for this scan.
6. IF `commit.sha` is missing, is not a string, or is not exactly 40 characters from `0-9`, `a-f` and `A-F` (EF-13), THEN THE Pipeline SHALL return the error `upstream-unavailable` with `details.source` equal to `github`.
7. IF a required discovery request (repository, branch or tree) ends as `failed` under Requirement 15 (after `RETRY_MAX_ATTEMPTS` attempts, or at once for an HTTP 4xx other than 429 and the throttle signals of EF-23, where an HTTP 404 of the repository request and of the branch request is handled by criteria 2 and 5 and an HTTP 404 of the tree request is a `failed` Work_Unit), or is not sent because GitHub_Budget is below `GITHUB_BUDGET_THRESHOLD` (Requirement 14, criterion 5), THEN THE Pipeline SHALL return the error `upstream-unavailable` with `details.source` equal to `github` and, only when `X-RateLimit-Reset` is an integer (EF-16), `details.resetAt` as that instant in ISO 8601 UTC. The one exception is a discovery request that ends `failed` with reason category `deadline` (cancelled or not started because of the scan deadline): THE Pipeline SHALL then return the error `deadline-exceeded` (Requirement 16, criterion 11).
8. THE Pipeline SHALL NOT store repository and branch responses in the Upstream_Cache and SHALL send a new repository request and a new branch request for every scan, so that Commit_SHA is always current.
9. IF the repository response (EF-12) is a 2xx answer with `private` not equal to true and `default_branch` is missing, is not a string, is empty, or is longer than `BRANCH_MAX_LENGTH` characters, while the Repo_Ref `branch` is null, THEN THE Pipeline SHALL return the error `upstream-unavailable` with `details.source` equal to `github`.
10. IF the body of a 2xx repository or branch response is not parsable JSON or is not a JSON object, THEN THE Pipeline SHALL return the error `upstream-unavailable` with `details.source` equal to `github`.
11. [PBT] THE Pipeline SHALL return, for every generated JSON value as the repository response and as the branch response, either a Commit_SHA of exactly 40 hexadecimal characters or one of the errors `repo-not-found`, `branch-not-found` and `upstream-unavailable`, and SHALL NOT throw.

### Requirement 4: Manifest discovery

**User Story:** As a developer, I want the repository's manifests listed, so that I can choose which to scan.

#### Acceptance Criteria

1. WHEN Commit_SHA is known, THE Pipeline SHALL request the recursive tree for Commit_SHA (EF-14).
2. THE Pipeline SHALL return as Manifest_Candidates the tree entries whose `path` is a non-empty string, whose `type` equals `blob`, and whose last path segment equals, case-sensitively, a name in `DISCOVERY_MANIFEST_NAMES` (EF-14), each with `path` equal to `tree[].path`, `format` equal to the core `ManifestFormat` of that file name, `depth` equal to the number of path segments minus 1, and `sizeBytes` equal to `tree[].size` when it is an integer at least 0, otherwise null.
3. THE Pipeline SHALL exclude every entry that has a directory segment (any segment other than the last) equal, case-sensitively, to a name in `DISCOVERY_SKIP_DIRS`, and SHALL NOT count such an entry toward `depthLimited` or `countLimited`.
4. THE Pipeline SHALL exclude every remaining entry whose `depth` exceeds `DISCOVERY_MAX_DEPTH` and SHALL set `depthLimited` to true when at least one entry was excluded for this reason, otherwise false.
5. WHEN more than `DISCOVERY_MAX_MANIFESTS` entries remain after criteria 2 to 4, THE Pipeline SHALL keep the first `DISCOVERY_MAX_MANIFESTS` in order of ascending `depth`, then ascending `path` in Unicode code point order, and SHALL set `countLimited` to true, otherwise false.
6. WHEN `truncated` equals the boolean true in the tree response (EF-14), THE Pipeline SHALL set `truncatedTree` to true and SHALL add a Scan_Note with code `tree-truncated` stating that the manifest list may be incomplete, and otherwise THE Pipeline SHALL set `truncatedTree` to false.
7. THE Pipeline SHALL return the Manifest_Candidates sorted by ascending `depth`, then ascending `path` in Unicode code point order.
8. WHEN no Manifest_Candidate remains and the request omits `manifests` or provides an empty list, THE Pipeline SHALL return a Scan_Result with empty `manifests`, `dependencies` and `assessed` lists and a Scan_Note with code `no-manifests`, and SHALL NOT return an error.
9. [PBT] THE Pipeline SHALL return, for every generated tree, a list whose length is at most `DISCOVERY_MAX_MANIFESTS`, whose every path has depth at most `DISCOVERY_MAX_DEPTH`, whose every path has no directory segment in `DISCOVERY_SKIP_DIRS`, and whose every path has a last segment in `DISCOVERY_MANIFEST_NAMES`.
10. [PBT] THE Pipeline SHALL return, for every generated tree, an equal Discovery_Result (candidates and the three flags) for any permutation of the tree entries.
11. IF the tree response body is not a JSON object, or its `tree` is missing or is not an array (EF-14), THEN THE Pipeline SHALL return the error `upstream-unavailable` with `details.source` equal to `github`, and SHALL count the Work_Unit as `failed` toward the github Source_Status.
12. [PBT] THE Pipeline SHALL return, for every generated JSON value as the tree response, either a Discovery_Result or the error of criterion 11, SHALL ignore every entry whose `path` or `type` is not a string, and SHALL NOT throw.
13. [PBT] THE Pipeline SHALL set, for every generated tree, `countLimited` to true if and only if more than `DISCOVERY_MAX_MANIFESTS` entries remain after criteria 2 to 4, and SHALL return in that case exactly the first `DISCOVERY_MAX_MANIFESTS` of the remaining entries in the order of criterion 7.

### Requirement 5: Manifest selection, fetching and parsing

**User Story:** As a developer, I want to scan the manifests I chose, defaulting to the root ones, so that a scan stays fast.

#### Acceptance Criteria

1. WHEN the request omits `manifests` or provides an empty list, THE Pipeline SHALL select every Root_Manifest among the Manifest_Candidates, in ascending `path` order in Unicode code point order.
2. WHEN the request omits `manifests` or provides an empty list, at least one Manifest_Candidate exists, and no Root_Manifest exists, THE Pipeline SHALL select no manifest and SHALL add a Scan_Note with code `no-root-manifest` whose `details` list every Manifest_Candidate path in the order of Requirement 4, criterion 7 (at most `DISCOVERY_MAX_MANIFESTS` paths). Requirement 4, criterion 8 applies instead when no Manifest_Candidate exists.
3. WHEN `manifests` is provided and is not empty, THE Pipeline SHALL select exactly the listed Manifest_Paths after removing duplicates, where two paths are duplicates only when they are equal as strings (case-sensitive, no normalization), and SHALL keep the first occurrence of each.
4. IF `manifests` contains more than `SCAN_MAX_MANIFESTS` distinct paths, THEN THE Pipeline SHALL return the error `too-many-manifests` with `details.limit` equal to `SCAN_MAX_MANIFESTS`, and SHALL send no manifest fetch request for this scan. This check precedes the check of criterion 5.
5. IF a listed path is not, compared exactly and case-sensitively, the `path` of a `blob` entry of the tree for Commit_SHA (EF-14), or its last path segment is not equal, case-sensitively, to a name in `DISCOVERY_MANIFEST_NAMES`, THEN THE Pipeline SHALL return the error `manifest-not-found` with `details.path` equal to the first such path in the order given in the request, and SHALL send no manifest fetch request for this scan. A listed path inside a Skipped_Directories directory or deeper than `DISCOVERY_MAX_DEPTH` is accepted when it satisfies this criterion.
6. IF the selection of criterion 1 holds more than `SCAN_MAX_MANIFESTS` Root_Manifests, THEN THE Pipeline SHALL select the first `SCAN_MAX_MANIFESTS` in ascending `path` order in Unicode code point order and SHALL add a Scan_Note with code `manifest-selection-capped`.
7. WHEN a manifest is selected and not skipped by criterion 8, THE Pipeline SHALL fetch its text at Commit_SHA one manifest at a time (Requirement 14, criterion 7) in ascending `path` order in Unicode code point order, from the source defined by Requirement 2, criterion 6 (EF-15), and SHALL pass the text and its core `ManifestFormat` to `parseManifest` unchanged.
8. IF the tree `size` of a selected manifest is an integer greater than the core `MAX_MANIFEST_LENGTH` (EF-14), THEN THE Pipeline SHALL send no fetch request for that manifest, SHALL skip it, SHALL add a Scan_Note with code `manifest-too-large` whose `details` hold the path, and SHALL NOT count a Work_Unit for it. A `size` equal to `MAX_MANIFEST_LENGTH`, or a null `size`, SHALL NOT cause a skip.
9. IF the fetch of one selected manifest ends as `failed` (after retries under Requirement 15, with HTTP 404 counted as `failed`, or not sent because GitHub_Budget is below `GITHUB_BUDGET_THRESHOLD` for a GHES blobs request under Requirement 14, criterion 3, or cancelled or not started because of the scan deadline under Requirement 16, criterion 5), THEN THE Pipeline SHALL continue with the other manifests, SHALL add a Scan_Note with code `manifest-fetch-failed` whose `details` hold the path, SHALL count the Work_Unit as not `ok` toward the github Source_Status, and SHALL NOT return an error for this reason. Requests to `GITHUB_RAW_HOST` SHALL NOT be blocked by GitHub_Budget (Requirement 14, criterion 11).
10. THE Pipeline SHALL include in the `manifests` list of the Scan_Result one entry per manifest that was fetched and parsed, with its `path`, its `format` and the `warnings` of its ParseResult unchanged and in the original order, and SHALL NOT include a manifest skipped by criterion 8 or failed by criterion 9.
11. THE Pipeline SHALL set the `ecosystem` of every Dependency only from the ParseResult and SHALL NOT infer it from the file path.
12. IF every selected manifest is skipped by criterion 8 or failed by criterion 9, THEN THE Pipeline SHALL return a Scan_Result with empty `manifests`, `dependencies` and `assessed` lists and the Scan_Notes of those criteria, and SHALL NOT return an error.
13. [PBT] THE Pipeline SHALL select, for every generated Manifest_Candidate list and every generated `manifests` list that passes criteria 4 and 5, a list of distinct Manifest_Paths whose length is at most `SCAN_MAX_MANIFESTS` and that is equal for every permutation of the candidate list, and, when `manifests` is omitted or empty, contains only Root_Manifests, and SHALL NOT throw.

### Requirement 6: Time and day arithmetic

**User Story:** As a maintainer, I want all ages computed from one instant, so that a scan is internally consistent and testable.

#### Acceptance Criteria

1. WHEN the Scan_Route accepts a request for scanning, THE Scan_Route SHALL capture asOf exactly once as an ISO 8601 UTC string with millisecond precision (`YYYY-MM-DDTHH:mm:ss.sssZ`) and SHALL pass that same value down as an argument, without capturing a second value during the same scan. The one exception is the `asOf` field of a Scan_Result served from the Scan_Cache, which keeps its original `asOf` (Requirement 19, criterion 6; Requirement 18, criterion 6).
2. THE Mappers SHALL NOT call `Date.now`, `performance.now`, `Date()`, `new Date()` without an argument, or any other function that reads the clock.
3. WHEN a date is a string that is a valid ISO 8601 UTC timestamp (format `YYYY-MM-DDTHH:mm:ss` with an optional fraction of 1 to 9 digits and the suffix `Z`, naming a calendar date and time that exist) and is not after asOf, THE Day_Count function SHALL return `floor((asOf - date) / DAY_MS)`, so that a date equal to asOf returns 0.
4. IF the date is a valid ISO 8601 UTC timestamp that is after asOf, THEN THE Day_Count function SHALL return 0 (see Open Question 2).
5. IF the date is not a string, is an empty string, or is a string that is not a valid ISO 8601 UTC timestamp as defined in criterion 3 (including a date without a time, a time zone offset other than `Z`, a second value of 60 or more, or a calendar date that does not exist such as `2023-02-30`), THEN THE Day_Count function SHALL return null.
6. [PBT] THE Day_Count function SHALL return, for every generated JSON value and every valid asOf, either null or an integer greater than or equal to 0, and SHALL NOT throw.
7. [PBT] THE Day_Count function SHALL return, for every date at most asOf, a value that does not decrease when the date moves earlier.
8. IF asOf is not a valid ISO 8601 UTC timestamp as defined in criterion 3, THEN THE Day_Count function SHALL return null and SHALL NOT throw.
9. [PBT] THE Day_Count function SHALL return, for every generated valid asOf, every generated integer `k` from 0 to 100000 and every generated integer `r` from 0 to `DAY_MS` - 1, the value `k` for the date that lies `k * DAY_MS + r` milliseconds before asOf.
10. [PBT] THE Day_Count function SHALL return, for every generated date and asOf, equal results on repeated calls with the same arguments.

### Requirement 7: Version selection

**User Story:** As a developer, I want the version looked up to match my manifest when it is pinned, so that vulnerabilities are reported for the version I use.

#### Acceptance Criteria

1. THE Pipeline SHALL treat a `versionSpec`, after removing leading and trailing whitespace, as an Exact_Pin only in these cases: for `npm`, `<v>` or `=<v>`; for `pypi`, `==<v>` or `===<v>`; for `cargo`, `=<v>`; and THE Pipeline SHALL take the Exact_Pin value to be `<v>` without the operator.
2. THE Pipeline SHALL accept `<v>` for `npm` and `cargo` only when it has the form `MAJOR.MINOR.PATCH`, where each part is a non-negative decimal integer without a leading zero (except `0` itself), optionally followed by `-` and a dot-separated pre-release list and optionally by `+` and a dot-separated build list, where every list item is 1 or more ASCII letters, digits or hyphens, and with no operator, wildcard, `*`, leading `v` or space. THE Pipeline SHALL accept `<v>` for `pypi` only when it is 1 or more characters, begins with an ASCII digit, and consists only of ASCII letters, digits and the characters `.`, `+`, `!`, `_` and `-`, so that it contains no `*`, space or `;`.
3. THE Pipeline SHALL NOT treat a bare Cargo `1.2.3` as an Exact_Pin, because Cargo reads it as a caret range, and SHALL select the default version for it (criterion 6).
4. WHEN a Lookup_Target has an Exact_Pin and a deps.dev `versions[]` entry has a `versionKey.version` string equal to the pinned string (EF-1), THE Pipeline SHALL set the Selected_Version to that string and Version_Basis to `pinned`. The comparison SHALL be exact and case-sensitive, with no normalization. If several entries match, the first in array order is used.
5. WHEN a Lookup_Target has an Exact_Pin and no `versions[]` entry has a `versionKey.version` equal to it (EF-1), THE Pipeline SHALL use the default version (criterion 6) as the Selected_Version, SHALL set Version_Basis to `default`, and SHALL add a Scan_Note with code `pin-not-found` whose `details` hold the ecosystem, the package name and the pinned string.
6. WHEN a Lookup_Target has no Exact_Pin, THE Pipeline SHALL use the default version as the Selected_Version and SHALL set Version_Basis to `default`. The default version is the latest release (deps.dev default version), and THE Pipeline SHALL NOT resolve any version from a lockfile or from a version range. The default version is the `versionKey.version` of the first `versions[]` entry, in array order, whose `isDefault` is the boolean true and whose `versionKey.version` is a non-empty string (EF-1).
7. WHEN one Lookup_Target appears in several manifests or scopes with different `versionSpec` values, THE Pipeline SHALL look up one Selected_Version for it. THE Pipeline SHALL ignore the values that are not Exact_Pins, and SHALL treat Exact_Pins as the same pin when their `<v>` strings are equal. THE Pipeline SHALL apply criterion 4 when exactly one distinct Exact_Pin exists, and otherwise SHALL apply criterion 6.
8. IF no Exact_Pin matched an entry and no entry qualifies as the default version under criterion 6 (EF-1), THEN THE Pipeline SHALL leave the Selected_Version unset, SHALL set Version_Basis to null, SHALL set `deprecated`, `openVulnerabilityCount`, `maxSeverity`, `archived` and `daysSinceLastCommit` to null (the Source_Repo is derived from the Selected_Version, Requirement 8), and SHALL add a Scan_Note with code `no-default-version` whose `details` hold the ecosystem and the package name, in addition to the `pin-not-found` note of criterion 5 when an Exact_Pin was not found.
9. THE Pipeline SHALL record, in the `lookupVersion` and `versionBasis` fields of every `dependencies` entry in the Scan_Result (Requirement 18), the checked version (the Selected_Version) and whether it came from an exact pin (`pinned`) or from the latest release (deps.dev default version, `default`), so that every Dependency with the same Lookup_Target receives equal values. THE Pipeline SHALL record null for both fields when the Selected_Version is unset or the Dependency is not looked up (Requirement 13, Requirement 16).
10. [PBT] THE Version_Selector SHALL return, for every generated `versionSpec` string (including null, empty, whitespace-only and non-string-like inputs) and every ecosystem, either null or the string `<v>` of criterion 1 without the operator, SHALL return a non-null value only for the patterns of criteria 1 and 2, and SHALL NOT throw.
11. IF the deps.dev package request ends with HTTP 404 or as a failed Work_Unit (EF-1), THEN THE Pipeline SHALL leave the Selected_Version unset, SHALL set Version_Basis to null, and SHALL NOT add a `pin-not-found` or `no-default-version` Scan_Note for that Lookup_Target. The notes and the fact values of this case are defined by Requirement 8 criterion 5 and Requirement 17 criteria 8 and 9.
12. IF more than one distinct Exact_Pin exists for one Lookup_Target (criterion 7), THEN THE Pipeline SHALL select the default version and SHALL add a Scan_Note with code `conflicting-pins` whose `details` hold the ecosystem, the package name and the distinct pinned strings in ascending Unicode code point order.
13. [PBT] THE Pipeline SHALL select, for every generated list of `versionSpec` values for one Lookup_Target and every permutation of that list, the same Selected_Version and Version_Basis.

### Requirement 8: Release and deprecation facts (deps.dev)

**User Story:** As a developer, I want release age and deprecation per package, so that stale and deprecated packages are flagged.

#### Acceptance Criteria

1. WHEN a Lookup_Target has `sourceKind` `registry`, THE depsdev Adapter SHALL send one package document request per Lookup_Target, using the system path segment `npm`, `pypi` or `cargo` that matches its ecosystem (EF-1).
2. THE Mapper SHALL set `daysSinceLastRelease` to the Day_Count of the latest instant among the `versions[].publishedAt` values for which Day_Count is not null (EF-1), ignoring entries that are not objects and entries with a missing or invalid `publishedAt`.
3. IF `versions` is missing, is not an array, is empty, or has no entry for which Day_Count of `publishedAt` is not null, THEN THE Mapper SHALL set `daysSinceLastRelease` to null (EF-1).
4. THE Mapper SHALL set `deprecated` to the boolean `isDeprecated` of the entry whose `versionKey.version` equals the Selected_Version by exact string comparison (EF-1), and to null when the Selected_Version is unset, no such entry exists, or `isDeprecated` is not a boolean. For a Lookup_Target of ecosystem `cargo`, an `unmaintained` advisory (EF-10) overrides this value with true under Requirement 9, criterion 6.
5. IF the deps.dev package request returns HTTP 404 (EF-1), THEN THE Pipeline SHALL set `daysSinceLastRelease`, `deprecated`, `openVulnerabilityCount`, `maxSeverity`, `archived` and `daysSinceLastCommit` of that Lookup_Target to null, SHALL send no OSV and no GitHub request for it, SHALL leave `maintainerCount` to Requirement 12, SHALL count the Work_Unit as `ok`, and SHALL add a Scan_Note with code `package-not-found` naming the package.
6. WHEN the ecosystem is `npm`, the deps.dev package request ended with a 2xx answer, Version_Basis is `default`, and the Mapper result for `deprecated` is null, THE Mapper SHALL read the `deprecated` field of the npm `/{name}/latest` response of Requirement 12 (EF-20) and SHALL set `deprecated` to true when the field is a non-empty string, to false when the field is absent or an empty string, and to null when the response is not a JSON object or the field has any other type (see Open Question 3).

WHEN the Selected_Version is set, THE depsdev Adapter SHALL request the version document (EF-2) for that Lookup_Target, batched through `versionbatch` in groups of at most `DEPSDEV_BATCH_SIZE` requests (EF-3), and THE Mapper SHALL set the Source_Repo to the `projectKey.id` of the first `relatedProjects[]` entry in array order whose `relationType` is `SOURCE_REPO` and whose id begins with `github.com/` followed by exactly two non-empty path segments (EF-2), and to absent when no entry qualifies or `relatedProjects` is missing or not an array.
8. IF a `versionbatch` request ends as `failed` after retries, returns a 2xx body that is not parsable JSON, or returns a body without a `responses` array (EF-3), or IF a request of the batch has no matching `responses[]` entry (criterion 9), THEN THE depsdev Adapter SHALL request each affected version document individually (EF-2) and THE Pipeline SHALL add one Scan_Note with code `batch-fallback` per scan, and SHALL count those individual requests, and not the replaced batch, toward the depsdev Source_Status.
9. THE Mapper SHALL match each `versionbatch` response to its request when `responses[].request.versionKey` has the same `name` and `version` and the same `system` compared case-insensitively, SHALL use the first matching entry in array order when several match, SHALL ignore entries that match no request, and SHALL NOT rely on response order (EF-3).
10. THE depsdev Adapter SHALL use the Lookup_Target `name` unchanged in every deps.dev request, and for `pypi` this name is the PEP503_Normalization of the manifest name, which equals the core `Dependency.name`.
11. [PBT] THE deps.dev Mappers SHALL return, for every generated JSON value as the response, an object whose fields are each null or of the declared type, and SHALL NOT throw.
12. [PBT] THE deps.dev Mappers SHALL set `daysSinceLastRelease` to null for every generated response in which `versions` is missing or no entry has a `publishedAt` (a missing field always maps to null).
13. [PBT] THE Mapper SHALL return, for every generated non-empty list of versions that each have a valid timestamp, a `daysSinceLastRelease` equal to the minimum Day_Count over the list, and the same value for every permutation of the list.
14. WHEN a Source_Repo is derived for a Lookup_Target (EF-2), THE Pipeline SHALL add a Scan_Note with code `source-repo-unverified` naming the package and the Source_Repo, stating that the link is unverified metadata.
15. IF a version document request ends as `failed` after retries, or the Selected_Version is unset, THEN THE Pipeline SHALL set the Source_Repo of that Lookup_Target to absent and SHALL leave `daysSinceLastRelease`, `deprecated` and the other facts of that Lookup_Target unchanged.
16. [PBT] THE Mapper SHALL return, for every generated `versionbatch` body and every permutation of its `responses`, equal Source_Repo results for each request (EF-3).

### Requirement 9: Vulnerability facts (OSV)

**User Story:** As a developer, I want the number and worst severity of open vulnerabilities for my version, so that risky dependencies stand out.

#### Acceptance Criteria

1. WHEN a Lookup_Target has a Selected_Version, THE osv Adapter SHALL query OSV with one query per Lookup_Target, with the package name equal to the Lookup_Target `name` and the version equal to the Selected_Version, both unchanged, ordered by ascending ecosystem, then ascending name in Unicode code point order. THE osv Adapter SHALL send the queries in batches of at most `OSV_BATCH_SIZE` using the ecosystem names `npm`, `PyPI` and `crates.io` (EF-5), and SHALL send no request when no Lookup_Target has a Selected_Version.
2. IF the length of `results` differs from the length of `queries` of the same batch (EF-5), THEN THE Pipeline SHALL count that Work_Unit as `failed`, SHALL set `openVulnerabilityCount` and `maxSeverity` to null for every Lookup_Target of that batch, SHALL send no advisory detail request for that batch, and SHALL continue the scan.
3. WHEN `results` and `queries` have equal length and `results[i]` is a JSON object whose `vulns` is missing or is an empty array, THE Mapper SHALL match `results[i]` to `queries[i]` by position (EF-5) and SHALL set `openVulnerabilityCount` to 0 and `maxSeverity` to null for that Lookup_Target.
4. WHEN a result has a non-empty `vulns` array, THE osv Adapter SHALL request the detail of each distinct non-empty string `vulns[].id` once per scan, across all Lookup_Targets (EF-6), and SHALL ignore entries without a non-empty string `id`. WHEN more than `OSV_MAX_ADVISORY_DETAILS` distinct ids exist, THE osv Adapter SHALL request the first `OSV_MAX_ADVISORY_DETAILS` ids in ascending Unicode code point order and SHALL leave the remaining ids unfetched.
5. THE Mapper SHALL exclude from the count and from `maxSeverity` an Advisory whose `withdrawn` is a non-empty string (EF-8), and SHALL treat an Advisory whose `withdrawn` is absent, empty, or not a string as not withdrawn.
6. THE Mapper SHALL exclude from the count and from `maxSeverity` an Advisory in which any `affected[]` entry has a string `database_specific.informational` (EF-10), whatever its value (`unmaintained`, `unsound`, `notice` or any other string). THE Pipeline SHALL add one Scan_Note with code `informational-advisory-excluded` per Lookup_Target that has at least one such Advisory. The `details` of the note SHALL hold the ecosystem, the package name and the excluded ids in ascending Unicode code point order. WHEN the ecosystem of the Lookup_Target is `cargo` and at least one fetched, non-withdrawn Advisory has an `affected[]` entry whose `database_specific.informational` equals exactly the string `unmaintained` (EF-10), THE Mapper SHALL set `deprecated` of that Lookup_Target to true, overriding a false or null value from deps.dev (Requirement 8, criterion 4), and THE Pipeline SHALL add one Scan_Note with code `unmaintained-advisory` per such Lookup_Target whose `details` hold the ecosystem, the package name and the ids of those Advisories in ascending Unicode code point order. Other `informational` values SHALL NOT change `deprecated`. IF the OSV detail of such an Advisory is not fetched (Requirement 9, criterion 9), THEN `deprecated` SHALL NOT be changed by this rule for that Advisory (decided in session 9, Open Question 4, closed).
7. THE Mapper SHALL build Alias_Groups from the Counted_Advisories of one Lookup_Target using `id` and the string items of `aliases` (EF-9). Two Counted_Advisories belong to the same Alias_Group when they are connected through any chain of shared ids or aliases. THE Mapper SHALL set `openVulnerabilityCount` to the number of Alias_Groups plus the number of unfetched ids (criterion 9). THE Mapper SHALL ignore a value that is not a JSON object, and an object without a non-empty string `id`, and SHALL ignore an `aliases` value that is not an array.
8. THE Mapper SHALL set `maxSeverity` to the highest Severity over the Counted_Advisories with a known severity (EF-7), using the order `LOW` < `MEDIUM` < `HIGH` < `CRITICAL`, and to null when none has a known severity. THE Mapper SHALL determine the severity of one Advisory by the ordered rules of Requirement 10, criterion 5: first the Advisory_Score (EF-25), otherwise `database_specific.severity` when it is exactly one of `LOW`, `MODERATE`, `HIGH` or `CRITICAL` (case-sensitive), otherwise the `severity[]` entries of type `CVSS_V3`, and otherwise as unknown (EF-7, EF-25).
9. IF an advisory detail request ends as `failed` after retries, ends with HTTP 404 (EF-6), is cancelled or not started because of the scan deadline (Requirement 16, criterion 5), or the id is left unfetched by criterion 4, THEN THE Mapper SHALL count each unfetched id of that Lookup_Target as its own vulnerability regardless of aliases, SHALL compute `maxSeverity` from the fetched Counted_Advisories only, and THE Pipeline SHALL count each such id as an Applicable_Unit of osv that did not end `ok` (Requirement 17, criteria 5 and 6, which also define the reason categories `deadline`, `truncated` and `http-error`) and SHALL add one Scan_Note per Lookup_Target with code `advisory-details-incomplete`. An id is unfetched only when its OSV detail (EF-6) is missing; a failed deps.dev advisory request (criterion 21) does not make an id unfetched. The `details` of the note SHALL hold the ecosystem, the package name and the unfetched ids in ascending Unicode code point order.
10. IF the Selected_Version is unset, THEN THE Pipeline SHALL set `openVulnerabilityCount` and `maxSeverity` to null and SHALL send no OSV request for that Lookup_Target.
11. IF a result contains a `next_page_token` key with a non-empty string value (EF-11), THEN THE Pipeline SHALL use the ids returned in that result without requesting further pages and SHALL add one Scan_Note per Lookup_Target with code `osv-pagination-ignored`, whose `details` hold the ecosystem and the package name. The osv Source_Status and the reason category `truncated` for this case are defined by Requirement 17, criteria 5 and 13.
12. [PBT] THE Mapper SHALL return, for every generated list of advisories, an `openVulnerabilityCount` that is an integer, at least 0 and at most the number of input advisories, and 0 when every advisory is withdrawn or informational.
13. [PBT] THE Mapper SHALL return, for every generated list of advisories and every permutation of it (and every permutation of each `aliases` array), equal `openVulnerabilityCount` and `maxSeverity`.
14. [PBT] THE Mapper SHALL return, for every generated list of Counted_Advisories with pairwise distinct ids and no shared aliases, to which one mutual alias link between two of them is added, an `openVulnerabilityCount` exactly one lower than for the list without the link.
15. [PBT] THE Mapper SHALL return, for every generated advisory without a valid Advisory_Score where `database_specific.severity` is `MODERATE`, the Severity `MEDIUM`, for `LOW`, `HIGH` and `CRITICAL` the same name (EF-7), and for any other string value the result of the `severity[]` rule of criterion 8.
16. [PBT] THE Mapper SHALL return, for every generated JSON value as an advisory, a result with `openVulnerabilityCount` null-or-integer and `maxSeverity` null-or-Severity, without throwing.
17. IF the OSV querybatch Work_Unit ends as `failed`, or `results[i]` is not a JSON object, or `results[i].vulns` is present and is not an array (EF-5), THEN THE Pipeline SHALL set `openVulnerabilityCount` and `maxSeverity` to null for the affected Lookup_Targets, SHALL send no advisory detail request for them, SHALL leave all other facts unchanged, and SHALL continue the scan without returning a Scan_Error (Requirement 17).
18. [PBT] THE osv Adapter SHALL request, for every generated set of querybatch results, at most `OSV_MAX_ADVISORY_DETAILS` advisory details, each distinct id at most once, and THE Mapper SHALL return an `openVulnerabilityCount` of at least the number of unfetched ids of that Lookup_Target.
19. [PBT] THE Mapper SHALL return, for every generated JSON value as the querybatch response and every list of queries (including lengths that differ), for each query either null facts or an `openVulnerabilityCount` that is an integer at least 0 with a `maxSeverity` that is null or a Severity, without throwing.
20. WHEN the set of advisory ids requested under criterion 4 is determined, THE depsdev Adapter SHALL send one advisory request (EF-25) per distinct id of that same set, once per scan across all Lookup_Targets, ordered by ascending Unicode code point order, with at most `CONCURRENCY_DEPSDEV` requests in flight. THE depsdev Adapter SHALL send no deps.dev advisory request for an id left unfetched by the `OSV_MAX_ADVISORY_DETAILS` cap, and SHALL count each request sent as an Applicable_Unit of depsdev (Requirement 17). An HTTP 404 answer (EF-25) SHALL end the Work_Unit as `ok` and SHALL leave the Advisory without an Advisory_Score.
21. IF a deps.dev advisory request ends as `failed` after retries, is cancelled or not started because of the scan deadline, or returns a body that is not a JSON object, THEN THE Mapper SHALL treat that Advisory as having no Advisory_Score and SHALL determine its severity by rules 2 to 4 of Requirement 10, criterion 5, THE Pipeline SHALL count the Work_Unit as an Applicable_Unit of depsdev that did not end `ok` (Requirement 17), and the Advisory SHALL still be counted or excluded by criteria 5 to 7 on the basis of its OSV detail.
22. [PBT] THE Mapper SHALL set, for every generated set of fetched advisories of a `cargo` Lookup_Target and every generated initial `deprecated` value (true, false or null), `deprecated` to true when at least one fetched, non-withdrawn advisory (counted or informational) has an `affected[]` entry with `database_specific.informational` equal exactly to `unmaintained`, and to the initial value otherwise (including when only `unsound`, `notice` or other informational values occur, and for every Lookup_Target of ecosystem `npm` or `pypi`), and SHALL add an `unmaintained-advisory` Scan_Note if and only if `deprecated` was set by this rule.
23. [PBT] THE depsdev Adapter SHALL send, for every generated set of querybatch results, at most `OSV_MAX_ADVISORY_DETAILS` advisory requests (EF-25), each distinct id at most once per scan.

### Requirement 10: Severity sources and CVSS v3 fallback

**User Story:** As a developer, I want a severity even when an advisory carries only a CVSS vector, so that severity is not unknown for most advisories.

#### Acceptance Criteria

1. THE CVSS_Function SHALL be a pure function (no clock, no I/O, no randomness) that converts a CVSS 3.0 or 3.1 base vector string into a base score from 0.0 to 10.0 with one decimal, using the CVSS 3.x specification formulas of the vector's own version, including that version's round-up function (EF-7). A vector is valid only if it has the exact, case-sensitive prefix `CVSS:3.0/` or `CVSS:3.1/`, followed by `/`-separated `KEY:VALUE` segments that contain each of the eight base metrics exactly once, in any order, with these values only: `AV` in `N`, `A`, `L`, `P`; `AC` in `L`, `H`; `PR` in `N`, `L`, `H`; `UI` in `N`, `R`; `S` in `U`, `C`; `C`, `I` and `A` each in `N`, `L`, `H`.
2. THE CVSS_Function SHALL map a base score to a Severity using `CVSS_RANGES`: 0.1 to 3.9 `LOW`, 4.0 to 6.9 `MEDIUM`, 7.0 to 8.9 `HIGH`, 9.0 to 10.0 `CRITICAL`.
3. IF the base score is 0.0, THEN THE CVSS_Function SHALL return null as the Severity.
4. IF the input is not a string, is an empty string, contains whitespace or an empty segment, has the prefix `CVSS:4.0/` or any prefix other than those of criterion 1, is malformed, lacks a base metric, repeats a metric, contains a metric key other than the eight base metrics, or has a metric value outside the lists of criterion 1, THEN THE CVSS_Function SHALL return null as the Severity and SHALL NOT throw (see Open Question 5).
5. THE Mapper SHALL determine the Severity of one Advisory by these rules, applied in this order, using the first rule that applies (EF-7, EF-25): (1) WHEN the Advisory has a valid Advisory_Score, the Severity of that score under criterion 14 (a score of 0.0 gives unknown and ends the evaluation); (2) otherwise, WHEN `database_specific.severity` equals, by exact case-sensitive comparison, `LOW`, `MODERATE`, `HIGH` or `CRITICAL`, the Severity of that value (`MODERATE` maps to `MEDIUM`), without evaluating any CVSS vector; (3) otherwise, the Severity from the `severity[]` entries of criterion 6; (4) otherwise, unknown. The OSV detail request (EF-6) remains required for the withdrawn, informational and alias data of every Advisory.
6. WHEN an Advisory has no valid Advisory_Score and no `database_specific.severity` value accepted by criterion 5 and has several `severity` entries, THE Mapper SHALL evaluate only entries whose `type` is the string `CVSS_V3` and whose `score` is a string, SHALL ignore every other entry, and SHALL use the highest Severity among the entries for which the CVSS_Function returns a Severity, ordered `LOW` < `MEDIUM` < `HIGH` < `CRITICAL` (EF-7).
7. IF an Advisory has no valid Advisory_Score, no `database_specific.severity` value accepted by criterion 5 and no `severity` entry for which the CVSS_Function returns a Severity, THEN THE Mapper SHALL treat the severity of that Advisory as unknown (EF-7), which Requirement 9 criterion 8 excludes from `maxSeverity`, and SHALL NOT fail the Work_Unit or the scan.
8. [PBT] THE CVSS_Function SHALL return, for every generated JSON value (including non-strings and arbitrary strings), null or a Severity, and SHALL NOT throw.
9. [PBT] THE CVSS_Function SHALL return, for every generated valid vector, a base score within 0.0 to 10.0 and the Severity that `CVSS_RANGES` assigns to that score, or null when the score is 0.0.
10. [PBT] THE CVSS_Function SHALL return, for every generated valid vector, a Severity that does not decrease when one impact metric (C, I or A) moves from `N` to `L` to `H` with all other metrics unchanged, where null ranks below `LOW`.
11. GitHub_Budget SHALL remain unknown after a response without an integer value (criterion 2).

### Requirement 15: Request resilience

**User Story:** As an operator, I want requests to be bounded and retried sensibly, so that slow or flaky upstreams do not stall the scan.

#### Acceptance Criteria

1. THE Adapters SHALL abort each HTTP attempt at the earliest of `REQUEST_TIMEOUT_MS` after the attempt was sent, `REQUEST_TOTAL_TIMEOUT_MS` after the first attempt of its Work_Unit was sent, and the abort of the Scan_Deadline_Signal (Requirement 16, criterion 5), and SHALL treat an attempt aborted by the first two bounds as a timeout and an attempt aborted by the Scan_Deadline_Signal as a deadline end (criterion 15). The time spent on the attempts, the waits and the response body reads of one Work_Unit SHALL NOT exceed `REQUEST_TOTAL_TIMEOUT_MS`.
2. IF the body of a response exceeds `MAX_RESPONSE_BYTES` bytes (a body of exactly `MAX_RESPONSE_BYTES` bytes is accepted), THEN THE Adapters SHALL stop reading, SHALL discard the bytes already read, SHALL end the Work_Unit as `failed` without a retry, and SHALL NOT pass any part of the body to a Mapper or to the Upstream_Cache.
3. THE Adapters SHALL keep the number of HTTP attempts in flight at or below the limit of the Upstream_Source: `CONCURRENCY_GITHUB` for `github`, `CONCURRENCY_DEPSDEV` for `depsdev`, `CONCURRENCY_OSV` for `osv`, `CONCURRENCY_NPM` for `npm`, `CONCURRENCY_CRATESIO` for `cratesio` and `CONCURRENCY_PYPI` for `pypi`. An attempt occupies a slot from the moment it is sent until its body is fully read, or it is aborted, or it fails. A wait between two attempts occupies no slot.
4. WHEN an attempt ends with HTTP 429, an HTTP status from 500 to 599, a network error or a timeout, THE Adapters SHALL send a further attempt of the same Work_Unit, up to `RETRY_MAX_ATTEMPTS` total attempts (see Open Question 8). IF the last permitted attempt also ends this way, THEN THE Adapters SHALL end the Work_Unit as `failed`. IF a further attempt ends with a 2xx answer or a 404 answer meaning "absent", THEN THE Adapters SHALL end the Work_Unit as `ok`.
5. IF an attempt ends with an HTTP 4xx status other than 429, THEN THE Adapters SHALL end the Work_Unit without a retry, with the exception of the GitHub throttle signals of EF-23 handled by criteria 7 and 8. An HTTP 2xx answer or a 404 answer meaning "absent" SHALL end the Work_Unit as `ok` after one attempt. Any other status SHALL end the Work_Unit as `failed` after one attempt.
6. WHEN a further attempt is due and criterion 7 does not apply, THE Adapters SHALL wait `floor(b + r * RETRY_JITTER_RATIO * b)` milliseconds before sending it, where `b = min(RETRY_BASE_DELAY_MS * 2^(n - 1), RETRY_MAX_DELAY_MS)`, `n` is the number of attempts made so far (n >= 1), and `r` is a value in the range 0 (inclusive) to 1 (exclusive) taken from the injected random function. IF the wait would end after the scan deadline (Scan_Start plus `SCAN_DEADLINE_MS`), THEN THE Adapters SHALL end the Work_Unit immediately as `failed` with reason category `deadline`, without waiting and without a further attempt. Otherwise, IF the wait would end after `REQUEST_TOTAL_TIMEOUT_MS` from the first attempt, THEN THE Adapters SHALL end the Work_Unit as `failed` without waiting.
7. WHEN an attempt ends with HTTP 429, or with a GitHub HTTP 403 that carries `Retry-After` (EF-23), and the response has `Retry-After` as a non-negative integer number of seconds, and a further attempt is permitted by criterion 4, THE Adapters SHALL wait that number of seconds (converted to milliseconds) instead of the delay of criterion 6, provided the wait is at most `RETRY_AFTER_MAX_MS`, the wait ends no later than `REQUEST_TOTAL_TIMEOUT_MS` after the first attempt, and the wait ends no later than the scan deadline (criterion 8 applies otherwise). A `Retry-After` value that is not a non-negative integer (for example an HTTP date) SHALL be ignored, and criterion 6 SHALL apply. A `Retry-After` header on any other status SHALL be ignored.
8. IF the `Retry-After` wait (criterion 7) would end after the scan deadline (Scan_Start plus `SCAN_DEADLINE_MS`), THEN THE Adapters SHALL end the Work_Unit immediately as `failed` with reason category `deadline`, without waiting and without a further attempt. Otherwise, IF `Retry-After` exceeds `RETRY_AFTER_MAX_MS`, or the wait would end after `REQUEST_TOTAL_TIMEOUT_MS` from the first attempt, THEN THE Adapters SHALL end the Work_Unit as `failed` without waiting and without a further attempt.
9. IF a response is an HTTP redirect whose target has a different origin (scheme, host or port) than the request URL, THEN THE Adapters SHALL NOT send any request to the target, SHALL NOT forward any request header to it, and SHALL end the Work_Unit as `failed` without a retry.
10. THE Adapters SHALL read the current time only from an injected clock, SHALL wait and abort only through an injected timer, SHALL receive the Scan_Deadline_Signal as an argument, and SHALL take random values only from an injected random function, so that tests with a fake clock, timer and random function complete every retry and timeout without real waiting.
11. [PBT] THE Retry_Policy SHALL make, for every generated sequence of attempt outcomes (statuses, network errors and timeouts), at most `RETRY_MAX_ATTEMPTS` attempts per Work_Unit.
12. [PBT] THE Retry_Policy SHALL make, for every generated sequence whose first outcome is not HTTP 429, an HTTP status from 500 to 599, a network error, a timeout or a GitHub throttle signal of EF-23, exactly one attempt.
13. [PBT] THE Retry_Policy SHALL return, for every generated attempt number n >= 1 and every generated random value r in the range 0 (inclusive) to 1 (exclusive), a delay `d` with `b <= d <= b * (1 + RETRY_JITTER_RATIO)`, where `b = min(RETRY_BASE_DELAY_MS * 2^(n - 1), RETRY_MAX_DELAY_MS)`, and therefore at most `RETRY_MAX_DELAY_MS * (1 + RETRY_JITTER_RATIO)`.
14. [PBT] THE Concurrency_Limiter SHALL keep, for every generated task set and every generated task duration, the number of simultaneous tasks at or below its limit, and SHALL run every task exactly once.
15. IF a Work_Unit ends as `failed` under this requirement, THEN THE Adapters SHALL report to the Pipeline a reason category, and THE Pipeline SHALL set the facts derived from that Work_Unit to null, SHALL continue the scan, and SHALL NOT throw (Requirement 17, criteria 7 and 9). The reason category SHALL be `timeout` when the last attempt was aborted by `REQUEST_TIMEOUT_MS` or `REQUEST_TOTAL_TIMEOUT_MS`, `network` when the last attempt ended with a network error, `rate-limited` when the end was caused by HTTP 429, a GitHub throttle signal or a `Retry-After` refused by criterion 8, and `http-error` in every other case (HTTP 5xx after the last attempt, HTTP 4xx, an oversize body, a cross-origin redirect). The Adapters report only these four categories, plus `budget` under criterion 17 and `deadline` for an attempt or wait ended by the Scan_Deadline_Signal or under criteria 6 to 8. THE Pipeline assigns the category `deadline` to Work_Units that have not started when the Scan_Deadline_Signal aborts, and the categories `token-missing`, `prerequisite` and `truncated` to Work_Units that it does not send or that it counts as incomplete (Requirement 17, criteria 5 and 9). An oversize body (criterion 2) is `http-error`.
16. THE Adapters SHALL start any two attempts to the `cratesio` source, including retry attempts, at least `CRATESIO_MIN_INTERVAL_MS` apart, measured on the injected clock.
17. IF a further attempt of a github Work_Unit is due and GitHub_Budget, as updated by the response of the previous attempt, is below `GITHUB_BUDGET_THRESHOLD`, THEN THE Adapters SHALL NOT send that attempt, SHALL end the Work_Unit as `failed` with reason category `budget`, and SHALL NOT wait (Requirement 14, criterion 3).
18. [PBT] THE Retry_Policy SHALL end, for every generated sequence of attempt outcomes, `Retry-After` values and fake clock readings in which a computed backoff or `Retry-After` wait would end after Scan_Start plus `SCAN_DEADLINE_MS`, the Work_Unit immediately with reason category `deadline`, with no timer wait scheduled and no further attempt sent.

### Requirement 16: Dependency cap and scan deadline

**User Story:** As an operator, I want a bounded amount of work per scan, so that one request cannot consume the quota or time.

#### Acceptance Criteria

1. THE Pipeline SHALL look up at most `SCAN_MAX_DEPENDENCIES` Lookup_Targets per scan, counting each Lookup_Target once after deduplication across the selected manifests.
2. WHEN more than `SCAN_MAX_DEPENDENCIES` Lookup_Targets exist, THE Pipeline SHALL look up the first `SCAN_MAX_DEPENDENCIES` ordered by ascending ecosystem, then ascending name, both compared as case-sensitive strings in Unicode code point order.
3. WHEN more than `SCAN_MAX_DEPENDENCIES` Lookup_Targets exist, THE Pipeline SHALL list every skipped Lookup_Target in `capped.skipped` of the Scan_Result with its ecosystem and name, in the order of criterion 2, SHALL set `capped.limit` to `SCAN_MAX_DEPENDENCIES` and `capped.total` to the number of Lookup_Targets before the cap, and SHALL add exactly one Scan_Note with code `dependency-cap-exceeded` whose `details` hold `capped.limit` and `capped.total`. A scan with exactly `SCAN_MAX_DEPENDENCIES` Lookup_Targets or fewer SHALL have an empty `capped.skipped`, `capped.limit` equal to `SCAN_MAX_DEPENDENCIES`, `capped.total` equal to the number of Lookup_Targets, and no `dependency-cap-exceeded` Scan_Note.
4. THE Pipeline SHALL keep every Dependency of a skipped Lookup_Target in the `AssessedDependency` list with a null classification and all-null `facts`, so that core reports them as unassessed, and SHALL send no request and count no Work_Unit for them (Requirement 13, criterion 8).
5. WHEN `SCAN_DEADLINE_MS` milliseconds have elapsed since Scan_Start on the injected clock, THE Pipeline SHALL abort the Scan_Deadline_Signal, and THE Adapters SHALL cancel every attempt in flight (including a body read in progress) and every backoff or `Retry-After` wait, for every Upstream_Source and including the Discovery_Requests, and SHALL send no further attempt. Every Deadline_Cancelled_Unit and every Deadline_Unstarted_Unit (including a Work_Unit that waits for a concurrency slot at that moment) SHALL end `failed` with reason category `deadline`, the facts derived from it SHALL be null, THE Pipeline SHALL continue the scan without throwing, and THE Pipeline SHALL add exactly one Scan_Note with code `scan-deadline-reached` per scan, however many Work_Units were cancelled or not started. A Work_Unit that ended before the abort keeps its result. This criterion applies to Applicable_Units for the Source_Status (Requirement 17, criteria 3, 4 and 5).
6. [PBT] THE Pipeline SHALL return, for every generated dependency list, a Scan_Result in which the number of looked-up Lookup_Targets is at most `SCAN_MAX_DEPENDENCIES`.
7. [PBT] THE Pipeline SHALL return, for every generated dependency list, a Scan_Result in which the looked-up Lookup_Targets and `capped.skipped` together equal the set of all registry Lookup_Targets with no loss and no repeat.
8. THE Adapters SHALL bind every outbound request to the Scan_Deadline_Signal, including each retry attempt, so that no Work_Unit sends an attempt and no attempt or wait remains pending at or after Scan_Start plus `SCAN_DEADLINE_MS`. A retry is part of its Work_Unit, is bound by the same signal, and SHALL NOT continue past the deadline. The per-Work_Unit bounds of Requirement 15, criteria 1 and 6, still apply in addition, and the GitHub budget rule of Requirement 15, criterion 17 SHALL still apply to every retry.
9. [PBT] THE Pipeline SHALL send, for every generated sequence of Work_Unit durations and clock readings (fake clock), no attempt of any Work_Unit, first attempt or retry, at or after `SCAN_DEADLINE_MS` since Scan_Start, SHALL end every Deadline_Cancelled_Unit and every Deadline_Unstarted_Unit as `failed` with reason category `deadline`, and SHALL NOT throw.
10. [PBT] THE Pipeline SHALL return, for every generated dependency list with more than `SCAN_MAX_DEPENDENCIES` Lookup_Targets, a Scan_Result in which every Lookup_Target in `capped.skipped` sorts after every looked-up Lookup_Target by the order of criterion 2, and `capped.total` equals the number of looked-up Lookup_Targets plus the length of `capped.skipped`.
11. THE Pipeline SHALL apply `SCAN_DEADLINE_MS` to the Discovery_Requests as to every other request (criterion 5). IF the Scan_Deadline_Signal aborts before the Commit_SHA and the manifest selection of Requirement 5 are both known, THEN THE Pipeline SHALL return the error `deadline-exceeded` (Requirement 21, criterion 6). IF it aborts after both are known, THEN THE Pipeline SHALL return a Scan_Result in which the unfinished facts are null and each Source_Status follows Requirement 17.
12. THE Scan_Route SHALL respond with a Scan_Result or a Scan_Error no later than `SCAN_RESPONSE_MARGIN_MS` after `SCAN_DEADLINE_MS`, measured from Scan_Start. After the Scan_Deadline_Signal aborts, THE Pipeline SHALL perform only in-memory work (mapping, classification, summarization and assembly from the Work_Units already completed) and SHALL NOT start any I/O (see Open Question 14).
13. [PBT] THE Pipeline SHALL return, for every generated simulated latency of every Upstream_Source (including requests that never respond) and every generated retry sequence, on a fake clock, a Scan_Result or a Scan_Error no later than Scan_Start plus `SCAN_DEADLINE_MS` plus `SCAN_RESPONSE_MARGIN_MS`, and SHALL abort every request still in flight at Scan_Start plus `SCAN_DEADLINE_MS`.

### Requirement 17: Source status and partial results

**User Story:** As a developer, I want to see which sources failed, so that I know how far to trust the result.

#### Acceptance Criteria

1. WHEN the Pipeline has ended every Work_Unit of a scan that returns a Scan_Result, THE Pipeline SHALL compute exactly one Source_Status, with a value of `ok`, `partial` or `failed`, for each of `github`, `depsdev`, `osv`, `npm`, `cratesio` and `pypi`, and SHALL return the six values in `sources` of the Scan_Result (Requirement 18, criterion 1). Every Work_Unit of the source counts toward its Source_Status, including the required discovery requests of Requirement 3, raw content requests to `GITHUB_RAW_HOST` and GraphQL requests, which all count toward `github`.
2. WHEN every Applicable_Unit of a source ended `ok`, or the source has no Applicable_Unit, THE Pipeline SHALL set the Source_Status of that source to `ok`.
3. IF a source has at least one Applicable_Unit, no Applicable_Unit of that source ended `ok`, and no Applicable_Unit of that source is a Deadline_Cancelled_Unit or a Deadline_Unstarted_Unit, THEN THE Pipeline SHALL set the Source_Status of that source to `failed`. The status `failed` is reserved for a source whose every Applicable_Unit ended `failed` for a reason category other than `deadline`.
4. IF a source has at least one Applicable_Unit that did not end `ok`, and either at least one Applicable_Unit of that source ended `ok` or at least one Applicable_Unit of that source is a Deadline_Cancelled_Unit or a Deadline_Unstarted_Unit, THEN THE Pipeline SHALL set the Source_Status of that source to `partial`, so that a source with deadline-cancelled or deadline-unstarted work is `partial` even when no unit of that source ended `ok`.
5. THE Pipeline SHALL count each of these as an Applicable_Unit that did not end `ok`, with the reason category given in brackets: a Work_Unit not sent because of the GitHub budget (`budget`), a Work_Unit cancelled or not started because the Scan_Deadline_Signal aborted (`deadline`, Requirement 16, criterion 5), a GraphQL request not sent because no Token is set (`token-missing`), a Work_Unit not sent because a prerequisite source failed (`prerequisite`), and each advisory id left unfetched by `OSV_MAX_ADVISORY_DETAILS` (`truncated`, Requirement 9, criteria 4 and 9). A Work_Unit that is not needed, because the Lookup_Target has no Selected_Version after an `ok` deps.dev answer or has no Source_Repo (Requirement 9, criterion 10; Requirement 11, criterion 7), is not an Applicable_Unit.
6. THE Pipeline SHALL count a Work_Unit that ended with HTTP 404 meaning "absent" (EF-1, EF-20, EF-21, EF-22, EF-25) as `ok` (a GraphQL alias with a `NOT_FOUND` error, EF-19, is counted by Requirement 11, criterion 5), with the exception of an advisory detail request that ended with HTTP 404 (EF-6), which THE Pipeline SHALL count as an Applicable_Unit that did not end `ok` with reason category `http-error` (Requirement 9, criterion 9).
7. IF an Upstream_Source fails (a Work_Unit of that source ends `failed`, or its Source_Status is `failed` or `partial`), THEN THE Pipeline SHALL set the facts derived from the failed Work_Units to null, SHALL leave every fact derived from other Work_Units unchanged, SHALL continue the scan, SHALL NOT return a Scan_Error for this reason, and SHALL NOT throw (Requirement 3 defines the only failures of a source that return a Scan_Error: the required discovery requests).
8. IF the deps.dev package request of a Lookup_Target ends `failed`, THEN THE Pipeline SHALL set `daysSinceLastRelease`, `deprecated`, `openVulnerabilityCount`, `maxSeverity`, `archived` and `daysSinceLastCommit` of that Lookup_Target to null, because the Selected_Version and Source_Repo are unknown, SHALL send no osv or GraphQL request for it, and SHALL count each osv and github Work_Unit that this prevents as an Applicable_Unit that did not end `ok` with reason category `prerequisite`. IF only the version document request (or the `versionbatch` request and its single-request fallback) of a Lookup_Target ends `failed`, THEN THE Pipeline SHALL apply Requirement 8, criterion 15, SHALL set `archived` and `daysSinceLastCommit` to null, SHALL send no GraphQL request for it, SHALL count each github Work_Unit that this prevents as an Applicable_Unit that did not end `ok` with reason category `prerequisite`, and SHALL keep the osv lookup for its Selected_Version.
9. WHEN a Source_Status is `partial` or `failed`, THE Pipeline SHALL add exactly one Scan_Note for that source, with code `source-partial` for `partial` and code `source-failed` for `failed`, and SHALL add no such note for a source with Source_Status `ok`. The `message` SHALL be built from a fixed template and SHALL NOT contain raw upstream text. The `details` SHALL hold `source` (the Upstream_Source name), `reasons` (the distinct reason categories of its Applicable_Units that did not end `ok`, in ascending Unicode code point order, each one of `timeout`, `network`, `rate-limited`, `http-error`, `budget`, `deadline`, `token-missing`, `prerequisite`, `truncated`), `failedUnits` and `applicableUnits` (integers). The reason category of a Work_Unit that ended `failed` under Requirement 15 is the category reported by the Adapter (Requirement 15, criteria 15 and 17).
10. [PBT] THE Pipeline SHALL return, for every generated subset of failing Upstream_Sources (including all six), a Scan_Result and SHALL NOT return an error or throw, as long as the required discovery requests succeed.
11. [PBT] THE Pipeline SHALL set, for every generated subset of failing sources, each facts field derived only from a failing source to null.
12. [PBT] THE Pipeline SHALL set, for every generated outcome set, a Source_Status that follows criteria 2, 3, 4 and 13, and SHALL add a `source-failed` or `source-partial` Scan_Note for a source if and only if its Source_Status is not `ok` (criterion 9).
13. WHEN a querybatch result contains a `next_page_token` key with a non-empty string value (EF-11, Requirement 9, criterion 11), THE Pipeline SHALL count that querybatch Work_Unit as `ok`, and IF the osv Source_Status would otherwise be `ok`, THEN THE Pipeline SHALL set it to `partial` and add a `source-partial` Scan_Note (criterion 9) with the reason category `truncated`, where `failedUnits` counts only Applicable_Units that did not end `ok`. THE Pipeline SHALL leave an osv Source_Status of `failed` or `partial` unchanged, and SHALL add the reason category `truncated` to the `reasons` of its note.
14. [PBT] THE Pipeline SHALL return, for every generated set of querybatch results and advisory id counts, an osv Source_Status of `partial` or `failed` whenever any result has a non-empty `next_page_token` or any advisory id is left unfetched, and a `reasons` list of the note that contains `truncated` in that case.
15. [PBT] THE Pipeline SHALL return, for every generated set of Work_Unit outcomes, a Scan_Result in which `reasons` of each `source-failed` or `source-partial` Scan_Note contains only the nine categories of criterion 9 and contains no duplicate.
16. [PBT] THE Pipeline SHALL return, for every generated set of Work_Unit outcomes that includes Deadline_Cancelled_Units and Deadline_Unstarted_Units, a Source_Status of `partial` for every source that has at least one such unit (whether or not any unit of that source ended `ok`), a Source_Status of `failed` only for a source whose every Applicable_Unit ended `failed` for a reason category other than `deadline`, and a `source-partial` Scan_Note whose `reasons` contain `deadline` for every such source.

### Requirement 18: Scan output

**User Story:** As a UI developer, I want one complete, explainable result, so that the UI needs no further data logic.

#### Acceptance Criteria

1. THE Pipeline SHALL return a Scan_Result that has exactly these top-level fields, each always present and never `undefined`:
   - `ok`: the boolean true.
   - `asOf`: a string.
   - `repo`: `{ host, owner, repo, branch, defaultBranch, commitSha }`. `host` is the Web_Host. `owner` and `repo` are in the case written in the request. `branch` is the selected branch, a non-null string that equals the requested branch when the request gave one and otherwise equals `defaultBranch` (EF-12). `defaultBranch` is `default_branch` (EF-12). `commitSha` is the Commit_SHA (EF-13).
   - `discovery`: the Discovery_Result `{ candidates, truncatedTree, depthLimited, countLimited }`.
   - `manifests`: one entry `{ path, format, warnings }` per manifest that was fetched and parsed (Requirement 5, criterion 10). A manifest that was skipped or whose fetch failed SHALL NOT appear in `manifests` and SHALL be reported only through its Scan_Note (Requirement 5, criteria 8 and 9).
   - `dependencies`: one entry `{ dependency, manifestPath, lookupVersion, versionBasis, facts }` per Dependency of each fetched and parsed manifest. `lookupVersion` is the checked version (the Selected_Version string) and `versionBasis` is `pinned` (exact pin) or `default` (latest release, the deps.dev default version). Both are null when the Selected_Version is unset or the Dependency is not looked up (Requirement 7, criterion 9).
   - `assessed`: the `AssessedDependency` list.
   - `summary`: the `RepoSummary`.
   - `sources`: an object with exactly the six keys `github`, `depsdev`, `osv`, `npm`, `cratesio` and `pypi`, each holding its Source_Status (Requirement 17, criterion 1).
   - `capped`: `{ limit, total, skipped }`. `limit` equals `SCAN_MAX_DEPENDENCIES`. `total` is the number of Lookup_Targets. `skipped` is the list of `{ ecosystem, name }` of every Lookup_Target skipped by Requirement 16, criterion 3, in the order of Requirement 16, criterion 2, and is an empty list when the cap does not apply.
   - `notes`: the list of Scan_Notes.
2. THE Pipeline SHALL set `facts` of each `dependencies` entry to the `RawHealthFacts` assembled by Requirement 13, or to all-null facts for a Dependency that is not looked up (a `git` or `path` Dependency, or a Dependency of a Lookup_Target skipped by the cap).
3. THE Pipeline SHALL set each `assessed` entry to the `AssessedDependency` of the `dependencies` entry at the same index, with its `Classification` unchanged from the core `classify` output, or null for a Dependency that is not looked up (Requirement 13, criteria 7 and 8).
4. THE Pipeline SHALL order `manifests` by ascending `path` in Unicode code point order, and SHALL order `dependencies` and `assessed` by ascending `manifestPath` in Unicode code point order, then by the core Dependency_Order within one manifest, with `assessed[i]` built from `dependencies[i]` for every index `i`.
5. THE Pipeline SHALL order `notes` by ascending `code` in Unicode code point order, then by ascending `details` text in Unicode code point order, where the `details` text is the JSON text of `details` with object keys in ascending Unicode code point order and the empty string when `details` is absent, so that equal inputs produce equal output.
6. THE Pipeline SHALL set `asOf` to the ISO 8601 UTC instant captured once for the scan by the Scan_Route (format of Requirement 6, criterion 1), except for a Scan_Result returned from the Scan_Cache, which keeps its original `asOf` (Requirement 19, criterion 6; Requirement 6, criterion 1).
7. [PBT] THE Pipeline SHALL return, for every generated set of upstream responses and asOf, equal Scan_Results on repeated runs (same inputs and asOf give the same result).
8. [PBT] THE Pipeline SHALL return, for every generated dependency list, a `summary` equal to the core `summarize` applied to `assessed`.
9. [PBT] THE Pipeline SHALL return, for every generated dependency list, an `assessed` list with the same length as the parsed Dependencies of the fetched and parsed manifests, and a `dependencies` list of that same length.
10. THE Pipeline SHALL return a Scan_Result that is JSON-serializable without loss, so that `JSON.parse(JSON.stringify(result))` equals the result, and that contains no `undefined`, `NaN` or infinite value, with every absent value represented as null.
11. WHEN no manifest was fetched and parsed (Requirement 4, criterion 8 or Requirement 5, criterion 12), THE Pipeline SHALL return a Scan_Result with empty `manifests`, `dependencies` and `assessed` lists, a `summary` equal to the core `summarize` applied to an empty list, an empty `capped.skipped` list, and the Scan_Notes of those criteria, and SHALL NOT return an error.
12. [PBT] THE Pipeline SHALL return, for every generated Scan_Result, a `dependencies` list in which every entry has `lookupVersion` and `versionBasis` both null or both non-null, and in which entries of one Lookup_Target have equal `lookupVersion` and `versionBasis`.

### Requirement 19: Caching

**User Story:** As an operator, I want repeated lookups to be served from memory, so that quotas last.

#### Acceptance Criteria

1. WHEN a request to depsdev, osv, npm, cratesio or pypi, or a GitHub tree, raw content or GraphQL request (EF-1, EF-5, EF-6, EF-14, EF-15, EF-17, EF-20, EF-21, EF-22, EF-25), ends with a 2xx answer or with an HTTP 404 answer that Requirement 17, criterion 6 counts as "absent", THE Upstream_Cache SHALL store the response body for `UPSTREAM_CACHE_TTL_SECONDS`, or, for an advisory detail response (EF-6 or EF-25), for `ADVISORY_CACHE_TTL_SECONDS` (criterion 17), counted from the instant that the injected clock returned when the body was stored.
2. IF a request ends with HTTP 429, an HTTP 5xx status, any other 4xx status that is not an "absent" 404, a network error or a timeout, or has a body larger than `MAX_RESPONSE_BYTES`, or is a GraphQL answer with an `errors[].type` other than `NOT_FOUND` (EF-19), or is a repository request or a branch request (EF-12, EF-13; Requirement 3, criterion 8), THEN THE Upstream_Cache SHALL NOT store anything for that request, and THE Upstream_Cache SHALL NOT store response headers for any request.
3. THE Upstream_Cache SHALL build each key from the Upstream_Source name, the HTTP method, the URL (which holds the advisory id for advisory detail requests) and the request body serialized with object keys in ascending order and array order preserved, and SHALL NOT include the Token, an `Authorization` header value or any other header in the key, so that two requests that differ only in the Token have equal keys.
4. THE Upstream_Cache SHALL include the Commit_SHA in the key of every GitHub tree request and the Commit_SHA and the Manifest_Path in the key of every GitHub raw content request (EF-14, EF-15), and SHALL store those responses for `UPSTREAM_CACHE_TTL_SECONDS` like every other entry.
5. WHEN the Pipeline has built a Scan_Result in which every one of the six Source_Status values is `ok` and no `github-token-missing` Scan_Note exists, THE Pipeline SHALL store that Scan_Result in the Scan_Cache for `SCAN_CACHE_TTL_SECONDS`, counted from the instant that the injected clock returned when it was stored, under the key (Web_Host, lowercase owner, lowercase repo, Commit_SHA, selected Manifest_Paths sorted ascending by Unicode code point), whether or not `capped.skipped` is empty.
6. WHEN a request has resolved to a Commit_SHA (Requirement 3) and its key matches a Scan_Cache entry that is not expired, THE Pipeline SHALL return the stored Scan_Result unchanged, including its original `asOf`, `sources` and `notes`, SHALL send no upstream request other than the repository request, the branch request and the tree request needed to determine the selected Manifest_Paths (the tree request is answered from the Upstream_Cache when an unexpired entry exists), and SHALL NOT change the expiry of the entry.
7. THE Pipeline SHALL NOT store in the Scan_Cache a Scan_Result in which any Source_Status is `partial` or `failed` or that has a `github-token-missing` Scan_Note (Open Question 22), and SHALL NOT store a Scan_Error in the Scan_Cache.
8. THE Scan_Cache key SHALL NOT include the Token or any value derived from it (for example a hash, a prefix or a length).
9. WHEN a new key is stored while the cache already holds `CACHE_MAX_ENTRIES` entries, THE Upstream_Cache and the Scan_Cache SHALL each evict the least recently used entry before storing, where a store or a successful read of an entry makes it the most recently used, and storing an existing key SHALL replace its value, SHALL restart its lifetime and SHALL NOT evict any other entry.
10. THE Upstream_Cache and the Scan_Cache SHALL read the current time, in milliseconds since the Unix epoch, only from an injected clock and SHALL NOT call `Date.now`, `performance.now`, `new Date()` without an argument or any other function that reads the clock, and SHALL treat an entry as expired when the injected clock returns a value earlier than the instant at which the entry was stored.
11. [PBT] THE Upstream_Cache and the Scan_Cache SHALL return, for every generated sequence of puts, gets and clock values with an injected clock, a value for a key if and only if the key was stored, its age (clock value minus storage instant) is at least 0 and less than the TTL in milliseconds (`UPSTREAM_CACHE_TTL_SECONDS`, `ADVISORY_CACHE_TTL_SECONDS` for advisory detail entries, or `SCAN_CACHE_TTL_SECONDS`, multiplied by 1000), and it was not evicted under criterion 9.
12. [PBT] THE Upstream_Cache and the Scan_Cache SHALL hold, for every generated sequence of operations, at most `CACHE_MAX_ENTRIES` entries each.
13. [PBT] THE Scan_Cache key function SHALL return, for every generated pair of requests that differ only in the Token, only in the letter case of owner or repo, or only in the order of the selected Manifest_Paths, equal keys, and SHALL return different keys for every generated pair that differ in Web_Host, in the lowercase owner or repo, in the Commit_SHA or in the set of selected Manifest_Paths.
14. WHEN a request to an Upstream_Source matches an Upstream_Cache entry that is not expired, THE Pipeline SHALL use the stored body without sending an HTTP request, SHALL count the Work_Unit as `ok` (Requirement 17), SHALL NOT change GitHub_Budget (EF-16, EF-18), and SHALL NOT occupy a concurrency slot (Requirement 15, criterion 3).
15. THE Upstream_Cache and the Scan_Cache SHALL NOT store the Token, an `Authorization` header value or any request header in any key or any value (Requirement 20, criterion 4).
16. [PBT] THE Pipeline SHALL return, for every generated scan whose six Source_Status values are `ok`, that has no `github-token-missing` Scan_Note, and that is repeated with the same Web_Host, owner, repo, Commit_SHA and selected Manifest_Paths before `SCAN_CACHE_TTL_SECONDS` have passed on the injected clock, a Scan_Result equal to the first one, and SHALL send no request other than those allowed by criterion 6.
17. THE Upstream_Cache SHALL store an advisory detail response, that is the OSV response of EF-6 and the deps.dev response of EF-25 (including a 404 answer of EF-25 counted as "absent"), under a key that holds the Upstream_Source name and the advisory id, for `ADVISORY_CACHE_TTL_SECONDS`, which is separate from and longer than `UPSTREAM_CACHE_TTL_SECONDS`. An OSV detail request that ends with HTTP 404 is not an "absent" answer (Requirement 17, criterion 6) and SHALL NOT be stored.
18. [PBT] THE Upstream_Cache SHALL return, for every generated sequence of advisory puts, gets and clock values, an advisory entry if and only if its age is at least 0 and less than `ADVISORY_CACHE_TTL_SECONDS` multiplied by 1000 and it was not evicted, and a non-advisory entry under the same clock values only while its age is less than `UPSTREAM_CACHE_TTL_SECONDS` multiplied by 1000.

### Requirement 20: Secrets

**User Story:** As an operator, I want the token to stay on the server, so that it cannot leak.

#### Acceptance Criteria

1. THE Pipeline SHALL read `GITHUB_TOKEN` only in one server-side token reader module, and no module that a client component imports, directly or through other modules, SHALL import the token reader.
2. THE github Adapter SHALL send the Token only as the value `Bearer ` followed by the Token in the `Authorization` header of requests whose URL has the scheme `https` and whose host (compared case-insensitively) is the host of `GITHUB_API_URL` or of `GITHUB_GRAPHQL_URL`, where criterion 11 makes these two hosts equal.
3. THE Adapters SHALL NOT send the Token or an `Authorization` header to `GITHUB_RAW_HOST`, deps.dev, OSV, npm, crates.io, PyPI, or any host named in the `Location` header of an HTTP redirect (3xx) answer, and the github Adapter SHALL NOT follow such a redirect with an `Authorization` header.
4. THE Pipeline SHALL NOT write the Token, or an `Authorization` header value, to any Secret_Sink.
5. THE Pipeline SHALL build every Scan_Error message and Scan_Note message from fixed templates and SHALL NOT include raw upstream response text or raw exception messages.
6. THE Logger SHALL receive only the structured fields source (an Upstream_Source name), status (an integer HTTP status or null), duration (integer milliseconds) and code (a string), SHALL NOT receive request headers, response headers, request bodies, response bodies or exception messages, and SHALL replace any `Authorization` header value in a received field with a fixed placeholder before writing a log line.
7. IF the Token is unset or an empty string, THEN THE Pipeline SHALL send every GitHub request that it sends without an `Authorization` header.
8. [PBT] THE Pipeline SHALL produce, for every generated Token of at least `TOKEN_TEST_MIN_LENGTH` characters and every generated scenario (including upstream stubs that echo request headers in bodies, in GraphQL `errors[].message` values and in error messages, and including 4xx, 5xx, timeout, redirect and unparsable-body answers), no Secret_Sink that contains the Token as a substring, where the test captures every log line written by the Logger, every returned and thrown error message, the serialized Scan_Result and Scan_Error, and every key and value of the Upstream_Cache and the Scan_Cache, and SHALL fail when any captured text contains the Token.
9. [PBT] THE Pipeline SHALL produce, for every generated Token and scenario of criterion 8, no Secret_Sink that contains the string `Bearer ` (compared case-insensitively) followed by the Token.
10. THE Pipeline SHALL NOT copy the Token into any environment variable whose name begins with `NEXT_PUBLIC_`, and no source file that references `GITHUB_TOKEN` SHALL contain the text `NEXT_PUBLIC_`.
11. IF the host of the GraphQL URL (compared case-insensitively, including any explicit port) is not equal to the host of the API URL, THEN THE Pipeline SHALL return the error `internal-error` (HTTP 500, Requirement 21) with a fixed message that names the variable `GITHUB_GRAPHQL_URL` and does not include its value, SHALL send no upstream request for that scan, and SHALL send the Token to no host, whether or not the Token is set.
12. THE Scan_Route SHALL NOT include the Token or an `Authorization` header value in any response body or any response header, and SHALL NOT include any `GITHUB_TOKEN` value in any data it passes to client code.
13. IF a response that the Fixture_Recorder is about to store contains the Token as a substring, or contains the string `Bearer ` followed by the Token, THEN THE Fixture_Recorder SHALL NOT write that Fixture, SHALL report a failure that does not contain the Token, and SHALL keep every previously stored Fixture unchanged.

### Requirement 21: Scan API

**User Story:** As a UI developer, I want a typed HTTP endpoint, so that the UI can show results and errors reliably.

#### Acceptance Criteria

1. THE Scan_Route SHALL expose `POST /api/scan`, which accepts a JSON body of the form `{ repoUrl: string, branch?: string, manifests?: string[] }`.
2. WHEN the request body has been parsed as a JSON value, THE Scan_Route SHALL treat the body as valid only if all of these hold, evaluated in this order:
   - (a) The value is a JSON object (not an array, `null`, string, number or boolean).
   - (b) Every own key is exactly `repoUrl`, `branch` or `manifests` (compared case-sensitively), so that any other key is an unknown field.
   - (c) `repoUrl` is present and is a string. The length and the form of `repoUrl` are checked by Requirement 1, not here.
   - (d) `branch`, when present, is a string. A `null` value is not a string.
   - (e) `manifests`, when present, is an array of at most `DISCOVERY_MAX_MANIFESTS` elements, each a string. An empty array is valid and has the meaning defined in Requirement 4, criterion 8 and Requirement 5, criterion 1. A `null` value is not an array. Duplicate strings count toward the maximum. The paths themselves are checked by Requirement 5.
3. IF a request fails one of these checks, THEN THE Scan_Route SHALL stop at the first failing check in the order given here and return the error `invalid-request` with the HTTP status and `details` given here. In that case THE Scan_Route SHALL send no upstream request and SHALL NOT capture asOf. The checks run after the method check of criterion 13.
   - (a) The `Content-Type` header is missing, or its media type (the text before the first `;`, trimmed, compared case-insensitively) is not `application/json`: HTTP 415, `details.reason` `unsupported-media-type`.
   - (b) The body is larger than `REQUEST_BODY_MAX_BYTES` bytes, measured on the declared `Content-Length` or on the bytes actually read, whichever shows the larger size (a body of exactly `REQUEST_BODY_MAX_BYTES` bytes is accepted): HTTP 413, `details.reason` `body-too-large`. THE Scan_Route SHALL stop reading and SHALL NOT parse the body.
   - (c) The body is empty, is not valid UTF-8, or is not parsable as JSON: HTTP 400, `details.reason` `invalid-json`.
   - (d) Criterion 2(a) fails: HTTP 400, `details.reason` `invalid-type`, `details.field` `body`.
   - (e) Criterion 2(b) fails: HTTP 400, `details.reason` `unknown-field`, `details.field` `body`. The unknown key name SHALL NOT be echoed.
   - (f) Criterion 2(c) fails because `repoUrl` is absent: HTTP 400, `details.reason` `missing-field`, `details.field` `repoUrl`.
   - (g) Criterion 2(c), 2(d) or 2(e) fails because of a wrong type of `repoUrl`, `branch` or `manifests`, or a non-string element of `manifests`: HTTP 400, `details.reason` `invalid-type`, `details.field` equal to the name of the first offending field in the order `repoUrl`, `branch`, `manifests`.
   - (h) `manifests` has more than `DISCOVERY_MAX_MANIFESTS` elements: HTTP 400, `details.reason` `too-many-items`, `details.field` `manifests`.
4. IF `branch` and a `/tree/<branch>` part of `repoUrl` are both present and are not equal as strings (case-sensitive, comparing the body value with the percent-decoded URL value of Requirement 1, criterion 2), THEN THE Scan_Route SHALL return HTTP 400 with the error `invalid-request`, `details.reason` `branch-conflict` and `details.field` `branch`, with a fixed-template message that contains neither branch name, and SHALL send no upstream request.
5. THE Scan_Route SHALL return, with the `Content-Type` `application/json`, a JSON body that is a discriminated union on `ok`: `{ ok: true, ...Scan_Result }` or `{ ok: false, error: { code, message, details? } }`. `message` SHALL be built from a fixed template (Requirement 20, criterion 5). `details` SHALL be omitted, not null, when criterion 6 defines no details for the code.
6. THE Scan_Route SHALL use exactly these error codes, HTTP statuses and `details` fields, and no other code, status or `details` field:
   - `invalid-request`: HTTP 400, 405, 413 or 415 as defined in criteria 3, 4 and 13. `details.reason` is one of `invalid-json`, `invalid-type`, `unknown-field`, `missing-field`, `too-many-items`, `branch-conflict`, `body-too-large`, `unsupported-media-type`, `method-not-allowed`. `details.field`, one of `body`, `repoUrl`, `branch`, `manifests`, is present for the reasons `invalid-type`, `unknown-field`, `missing-field`, `too-many-items` and `branch-conflict`, and absent for the others.
   - `invalid-url`: HTTP 400. `details.part` is one of `url`, `host`, `path`, `owner`, `repository`, `branch` (Requirement 1, criteria 5 to 10, and criterion 14 below).
   - `too-many-manifests`: HTTP 400. `details.limit` is `SCAN_MAX_MANIFESTS` (Requirement 5, criterion 4).
   - `manifest-not-found`: HTTP 404. `details.path` is the first offending path as given in the request (Requirement 5, criterion 5).
   - `repo-not-found`: HTTP 404, no `details` (Requirement 3, criterion 2).
   - `branch-not-found`: HTTP 404, no `details` (Requirement 3, criterion 5).
   - `upstream-unavailable`: `details.source` is an Upstream_Source name (Requirement 3, criteria 6, 7, 9 and 10; Requirement 4, criterion 11; Requirement 14, criterion 5). `details.resetAt` is an ISO 8601 UTC instant and is present only when Requirement 3, criterion 7 provides it. IF `details.resetAt` is present and later than asOf, THEN THE Scan_Route SHALL return HTTP 503 with a `Retry-After` header holding `ceil((resetAt - asOf) / 1000)` as a decimal integer of at least 1. Otherwise THE Scan_Route SHALL return HTTP 502 without a `Retry-After` header.
   - `deadline-exceeded`: HTTP 504, no `details`, no `Retry-After` header. Returned when the Scan_Deadline_Signal aborts before the Commit_SHA and the manifest selection are known (Requirement 16, criterion 11; Requirement 3, criterion 7).
   - `internal-error`: HTTP 500, no `details`. A configuration error (Requirement 2, criteria 4 and 9; Requirement 20, criterion 11) names the variable in the message and does not include its value.
7. WHEN a scan completes, including a scan with failed or partial sources, with no manifest (Requirement 4, criterion 8; Requirement 5, criterion 12), or served from the Scan_Cache (Requirement 19, criterion 6), THE Scan_Route SHALL return HTTP 200 with the Scan_Result.
8. IF an unexpected exception occurs anywhere in the handling of a request, including an exception thrown by the Pipeline, THEN THE Scan_Route SHALL return HTTP 500 with the error `internal-error` and a fixed message, and SHALL NOT include the exception message, the stack or the Token in the response.
9. THE Scan_Route SHALL set `Cache-Control: no-store` on every response, including every error response.
10. THE Scan_Route SHALL contain no scan logic beyond the checks of criteria 2 to 4, 13 and 14, asOf capture (Requirement 6, criterion 1, after the checks of criteria 3, 4 and 13 have passed), a call to the Pipeline entry function, and response formatting.
11. THE Scan_Route SHALL run in a server-side runtime that provides the Node.js APIs the Pipeline needs (Requirement 20, criterion 1). The framework mechanism is defined in the design phase.
12. [PBT] THE Scan_Route SHALL return, for every generated request (any method, any `Content-Type` value, any body bytes including arbitrary JSON, arbitrary strings and bodies around `REQUEST_BODY_MAX_BYTES`), a body that matches the discriminated union of criterion 5, an HTTP status in the set 200, 400, 404, 405, 413, 415, 500, 502, 503, 504, a status that matches the code according to criterion 6, only the `details` fields allowed for that code, and `Cache-Control: no-store`, and SHALL NOT throw.
13. IF the request method is not `POST` (including `GET`, `HEAD`, `PUT`, `PATCH`, `DELETE` and `OPTIONS`, compared case-sensitively), THEN THE Scan_Route SHALL return HTTP 405 with the error `invalid-request`, `details.reason` `method-not-allowed`, and the header `Allow: POST`, SHALL NOT read or validate the body, and SHALL send no upstream request.
14. WHEN a request has passed the checks of criteria 2 and 3, THE Scan_Route SHALL apply these steps in this order, and SHALL stop at the first one that returns an error:
    - (a) Read the GitHub configuration (Requirement 2). A configuration error returns `internal-error`, so a configuration error takes precedence over `invalid-url`.
    - (b) Pass `repoUrl` to the URL_Parser (Requirement 1) and return its `invalid-url` error unchanged.
    - (c) Check `branch`, when present, against the rules of Requirement 1, criterion 10, applied to the string as given (no percent-decoding), and also require at least 1 Unicode code point. A violation returns `invalid-url` with `details.part` `branch`.
    - (d) Apply criterion 4.
    - (e) Pass to the Pipeline one Repo_Ref whose `branch` is the body `branch` when present, otherwise the URL branch, otherwise null. When both are present and equal, that shared value is used.
15. [PBT] THE Scan_Route SHALL pass, for every generated valid `repoUrl` (with or without a `/tree/<branch>` part) and every generated `branch` that is absent or valid, a Repo_Ref whose `branch` equals the body `branch` when only the body provides one, equals the URL branch when only the URL provides one, and equals the shared value when both are present and equal. For every generated pair of present and unequal values, THE Scan_Route SHALL return `invalid-request` with `details.reason` `branch-conflict` and SHALL send no upstream request.

### Requirement 22: Architecture rules

**User Story:** As a maintainer, I want enforced module boundaries, so that the pure core stays pure.

#### Acceptance Criteria

1. THE Pipeline SHALL put all network code in `/adapters`, each Adapter behind a Source_Port declared in `/pipeline/ports` and named `<Name>Source` (`GithubSource`, `DepsDevSource`, `OsvSource`, `NpmSource`, `CratesIoSource`, `PypiSource`).
2. THE Pipeline SHALL put all Mappers in `/pipeline/mapping`, and every file in `/pipeline/mapping` SHALL import only from `/core`, from other files in `/pipeline/mapping` and from `/pipeline/constants.ts` (Requirement 13, criterion 1), so that no file there imports `/adapters`.
3. THE Pipeline SHALL NOT modify any file in `/core`.
4. THE `/core` module SHALL NOT import from `/pipeline`, `/adapters`, `/app` or `/components`.
5. THE Pipeline orchestrator SHALL receive Source_Port implementations, the clock, the timer, the random function, the cache and the Logger as constructor or function arguments.
6. WHEN an architecture test runs, THE test SHALL fail if any file in `/pipeline/mapping` imports from `/adapters` or uses `fetch`, `fs`, `Date.now`, `Math.random` or `process.env`.
7. WHEN an architecture test runs, THE test SHALL fail if any file in `/core` imports from `/pipeline`, `/adapters`, `/app` or `/components` (criterion 4).
8. WHEN an architecture test runs, THE test SHALL fail if any `.ts` or `.tsx` file in `/pipeline` or `/adapters` has a file name that is not one or more segments of lowercase ASCII letters and digits joined by single hyphens followed by the extension, or contains `export default` or `export =`, except the Scan_Route file.
9. WHEN an architecture test runs, THE test SHALL fail if any file in `/adapters` imports from `/pipeline/mapping`, from a file in `/pipeline` other than `/pipeline/ports` and `/pipeline/constants.ts`, from `/app` or from `/components`.
10. WHEN an architecture test runs, THE test SHALL fail if any file in `/core`, `/pipeline`, `/app` or `/components`, other than the Scan_Route file, imports from `/adapters`.
11. WHEN an architecture test runs, THE test SHALL fail if `/pipeline/ports` does not export an interface for each of the six Source_Port names of criterion 1, or if any file in `/pipeline/ports` imports from anything other than `/core`, other files in `/pipeline/ports` and `/pipeline/constants.ts`.
12. WHEN an architecture test runs, THE test SHALL fail if any file in `/pipeline` uses `fetch`, `XMLHttpRequest`, `Date.now`, `Math.random`, `performance.now`, `setTimeout`, `setInterval`, `Date()` or `new Date()` without an argument, or imports `http`, `https`, `http2`, `net`, `tls`, `dns` or `dgram`, with or without the `node:` prefix.
13. THE architecture test SHALL find imports by parsing source text only, without executing code and without network access, and SHALL treat as imports every `import` and `import type` declaration, every `export ... from` declaration, every `import x = require()` declaration, every `import()` type, every dynamic `import()` call and every `require()` call.
14. THE architecture test SHALL resolve each relative specifier and each `@/` specifier to a path relative to the project root and compare it with a directory on whole path segments, SHALL report a module specifier that is not a string literal as a violation, SHALL report each violation with the file path, the 1-based line and a rule identifier, and SHALL NOT throw for any input text, including text with syntax errors.
15. [PBT] THE architecture test SHALL report, for every generated file path in each layer of criteria 2, 4, 9, 10 and 11, every generated specifier form listed in criterion 13 and every generated `../` depth, at least one violation on the line of the import when the specifier resolves to a directory the layer must not import, SHALL report no import violation when it resolves to an allowed directory, and SHALL return equal results on repeated calls with the same input.
16. WHEN the CI workflow runs, THE architecture test SHALL run together with the existing `/core` purity check, and a reported violation SHALL fail the CI run.
17. WHEN an architecture test runs, THE test SHALL fail if more than one source file contains the text `process.env.GITHUB_TOKEN`, if any file that begins with the `'use client'` directive imports, directly or through other modules, the one file that contains that text, or if any source file that references `GITHUB_TOKEN` contains the text `NEXT_PUBLIC_` (Requirement 20, criteria 1 and 10).

### Requirement 23: Testing and fixtures

**User Story:** As a maintainer, I want offline, recorded tests, so that CI is stable and free of network access.

#### Acceptance Criteria

1. THE test suite SHALL run offline: a global `fetch` stub SHALL throw an error and SHALL make the calling test fail when any test performs a network request that no test-provided stub or Fixture_Replay serves. The only exceptions are the live contract tests of criterion 8 and the Fixture_Recorder of criterion 10, which run only when the Live_Tests_Flag equals `1`.
2. THE test suite SHALL include Fixtures from at least `FIXTURE_MIN_REPOS` distinct real public GitHub repositories, with at least one repository for each of these three kinds: an npm project (manifest `package.json`), a Python project (manifest `requirements.txt`) and a Rust project (manifest `Cargo.toml`). Each repository SHALL have at least one Lookup_Target that, at the recorded asOf, has `archived` true or `deprecated` true in the recorded facts.
3. THE Fixtures SHALL contain the recorded response of every Endpoint_Fact_Map request that the scan of that repository sends, stored under `/tests/fixtures/<repo>/`, together with a metadata file that holds the recording time (ISO 8601 UTC), the asOf of the recording (ISO 8601 UTC), the Canonical_Repo_URL and the kind of the repository (npm, Python or Rust). IF a fixture test makes a request for which no Fixture response exists, THEN THE Fixture_Replay SHALL fail that test with an error that names the Upstream_Source, and SHALL NOT fall back to the network.
4. WHEN the fixture test of a repository runs with the recorded asOf, THE Pipeline SHALL produce a Scan_Result with `ok` true in which at least one entry of `dependencies` has `facts.archived` true or `facts.deprecated` true.
5. WHEN a fixture test runs the same scan twice with the recorded asOf, each run starting with an empty Upstream_Cache and an empty Scan_Cache, THE Pipeline SHALL produce two Scan_Results that are deeply equal.
6. WHEN the Fixture scan test runs, THE test SHALL read every file under `/tests/fixtures` recursively and SHALL fail if any file contains a request header named `Authorization` (compared case-insensitively), the string `Bearer `, a GitHub token pattern (`ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`, `github_pat_`), or, when `GITHUB_TOKEN` is set and not empty, the value of `GITHUB_TOKEN`. This test SHALL run in every test run, whatever the value of the Live_Tests_Flag.
7. THE Fixture_Recorder SHALL store only response bodies and the response headers `content-type`, `retry-after` and `x-ratelimit-*` (compared case-insensitively), and SHALL NOT store any request header or any other response header. A unit test SHALL feed the recorder a response with additional headers (including `Authorization`, `set-cookie` and `x-request-id`) and SHALL check that none of them is stored.
8. WHERE the Live_Tests_Flag equals `1`, THE test suite SHALL run live contract tests that call the real upstreams and check that every field path listed in the Endpoint_Fact_Map rows of criterion 13 (verified rows) exists in the live response of that row, using the same repositories and packages as the Fixtures. A live test SHALL pass for a row only when all field paths of that row exist.
9. IF the Live_Tests_Flag is unset or has any value other than `1`, THEN THE test suite SHALL report each live contract test as skipped (not as passed) and SHALL NOT make any network request.
10. THE Fixture_Recorder SHALL run only when the Live_Tests_Flag equals `1`.
11. THE unit tests SHALL verify, by reading the exported values of `/pipeline/constants.ts`, each of the six constant consistency rules of the Constants section as a separate test case, and SHALL fail when a constant named in a rule is not exported. For the rule on batch sizes and maxima, the test SHALL check every exported constant whose name ends with `_BATCH_SIZE`, contains `_MAX_` or begins with `MAX_`.
12. THE unit tests SHALL cover, with stubbed Source_Ports, these cases with these outcomes:
    1. an unauthenticated scan with no Token: `archived` and `daysSinceLastCommit` are null for every Lookup_Target, no GraphQL request is sent, and exactly one Scan_Note with code `github-token-missing` exists (Requirement 11, criterion 8);
    2. a truncated tree (`truncated` true, EF-14): the Discovery_Result has `truncatedTree` true and a `tree-truncated` Scan_Note exists (Requirement 4, criterion 6);
    3. a GraphQL partial answer with one `NOT_FOUND` alias: that Source_Repo has null `archived` and `daysSinceLastCommit`, the other aliases keep their data, and no `source-failed` or `source-partial` Scan_Note is added for it (Requirement 11, criterion 5);
    4. a renamed repository: the Lookup_Target receives the data of the repository that GraphQL resolved (Requirement 11, criterion 2);
    5. a 404 package: all facts of EF-1 are null and the Work_Unit ends `ok` (EF-1);
    6. a 429 with `Retry-After` at most `RETRY_AFTER_MAX_MS`: the Adapter waits that many seconds on the injected timer and sends a further attempt (Requirement 15, criterion 7);
    7. a 429 with `Retry-After` above `RETRY_AFTER_MAX_MS`: the Work_Unit ends `failed` with reason category `rate-limited`, with no wait and no further attempt (Requirement 15, criterion 8);
    8. a GitHub_Budget drop below `GITHUB_BUDGET_THRESHOLD` during the scan: no further GitHub request is sent, and exactly one Scan_Note with code `github-budget-low` exists (Requirement 14, criterion 4);
    9. an informational RustSec advisory (EF-10): it is not counted in `openVulnerabilityCount` and an `informational-advisory-excluded` Scan_Note exists (Requirement 9, criterion 6);
    10. a `cargo` Lookup_Target with an `unmaintained` RustSec advisory (RUSTSEC-2020-0036, EF-10) and deps.dev `isDeprecated` false: `deprecated` is true, an `unmaintained-advisory` Scan_Note names the advisory id, and the count excludes it; the same advisory with `informational` `unsound` leaves `deprecated` false (Requirement 9, criterion 6);
    11. an upstream that never responds: at Scan_Start plus `SCAN_DEADLINE_MS` on the fake clock the request is aborted, the source is `partial` with reason `deadline`, exactly one `scan-deadline-reached` Scan_Note exists, and a deadline before the Commit_SHA is known returns `deadline-exceeded` with HTTP 504 (Requirement 16, criteria 5 and 11);
    12. a deps.dev advisory with `cvss3Score` 9.8 and an OSV advisory with `database_specific.severity` `LOW`: `maxSeverity` is `CRITICAL`; the same advisory with the deps.dev request failed: `maxSeverity` is `LOW` (Requirement 10, criterion 5).
13. THE test suite SHALL contain, for every Endpoint_Fact_Map row whose Verification column begins with "Verified live (HTTP), not via MCP" and that a Mapper or the Pipeline uses (every such row except EF-4), at least one Fixture response that contains every field path of that row, and a test that fails and names the row ID and the missing field path when a field path is not present in any Fixture. Where a field path is absent from normal responses (`withdrawn` of EF-8, `affected[].database_specific.informational` of EF-10, and `errors[]` of EF-19), a supplementary Fixture recorded from an advisory or a repository alias that produces that field SHALL exercise it. The test SHALL NOT require field paths or behaviours that the Verification column marks as "Not verified": scoped-name encoding (EF-1, EF-20), branch names with `/` (EF-13), a non-empty `nextPageToken` (EF-3), GHES (EF-15), the `organization` value type (EF-22), error types other than `NOT_FOUND` (EF-19), and an absent or non-number `cvss3Score` and advisory id path encoding (EF-25). For EF-25 the required field paths are `advisoryKey.id` and `cvss3Score`. Rows EF-11, EF-23 and EF-24 are marked Not verified and need no Fixture.
14. IF the Live_Tests_Flag equals `1` and `GITHUB_TOKEN` is unset or empty, THEN THE test suite SHALL report the live contract tests of the rows that require a token (EF-17, EF-18, EF-19) as skipped with a reason that names the missing token, and SHALL run the other live contract tests.
15. IF a live contract test finds that a field path of a verified row is missing, THEN THE test SHALL fail with a message that names the row ID, the Upstream_Source and the missing field path, and SHALL NOT include the response body, the Token or an `Authorization` header value in the message or in any Fixture.

## Open questions for review

Each question has a recommended default, which this document already applies.

1. **Version looked up (major). Closed (session 9).** Decision: exact pins use the pinned version, everything else uses the latest release (deps.dev default version), and `versionBasis` is recorded (Requirement 7). Lockfiles are out of scope and never used to resolve a version. Consequence: for ranged dependencies the vulnerability count reflects the latest release, not the version a lockfile would install.
2. **Date after asOf.** Recommended: Day_Count returns 0 (clock skew between GitHub or the registry and the server is the likely cause, and a very recent date is the closest true meaning). Alternative: null.
3. **Deprecation source.** Recommended: deps.dev `isDeprecated` of the Selected_Version; the npm `deprecated` field only as fallback for npm with the default basis when deps.dev gives no value. Alternative: OR both sources.
4. **RustSec informational advisories. Closed (session 9).** Decision: informational advisories are not vulnerabilities and are excluded from counts, with an `informational-advisory-excluded` note. Exception: an advisory with `informational` equal to `unmaintained` sets `deprecated` to true for the cargo crate, with an `unmaintained-advisory` note (Requirement 9, criterion 6). This raises `abandoned` in core for crates such as `failure`.
5. **CVSS v4.** Recommended: unknown (null). Alternative: implement the CVSS v4 scoring tables, which is a larger pure function.
6. **PyPI maintainer count. Closed (session 9).** Decision: include it, from `ownership.roles` (EF-22, Requirement 12, criterion 5).
7. **crates.io teams. Closed (session 9).** Decision: count only `kind` `user`, a teams-only list is unknown, users plus teams is a lower bound with a Scan_Note (Requirement 12, criteria 3 and 4).
8. **Retry on network errors and timeouts.** Recommended: retry them, together with 429 and 5xx, within `RETRY_MAX_ATTEMPTS`. Alternative: only 429 and 5xx.
9. **Where the Source_Ports live.** `tech.md` says adapters implement interfaces defined in `/core`, but this spec leaves `/core` unchanged. Recommended: declare them in `/pipeline/ports`. Alternative: add the interfaces to `/core` in a separate change.
10. **GitHub Enterprise Server raw content.** Recommended: use the blobs API of the API URL, which consumes GitHub budget. Both the host layout (EF-24) and the blob response were not verified.
11. **Scan_Cache storage rule.** Recommended: cache only scans with every source `ok`. Consequence: scans without a token (github `partial`) are never scan-cached, though upstream responses still are.
12. **Query strings.** Recommended: only `tab` is ignored (`URL_IGNORED_QUERY_PARAMS`); every other parameter is rejected. Alternative: reject every query string.
13. **No-token mode.** Discovery uses the REST tree at 60 requests per hour per server IP (three requests per scan: repository, branch, tree), so about 20 scans per hour without a token. Recommended: accept and show the `github-token-missing` note.
14. **Scan deadline (replaced in session 9).** One deadline, `SCAN_DEADLINE_MS` = 25000, with `SCAN_RESPONSE_MARGIN_MS` = 1500 as the response margin. Every request, retry and wait, including discovery, is cancelled at the deadline through an abort signal tied to the scan deadline (Requirement 16). The deadline is far below the hosting function duration limit; the design phase checks the limit of the chosen hosting plan and no specific number is asserted here. Recommended: keep 25000 and 1500, and review them after the first live measurements.
15. **deps.dev batch endpoint.** `v3alpha/versionbatch` is unstable. Recommended: use it with the single-request fallback of Requirement 8, criterion 8. Alternative: single requests only.
16. **Pinned version not in the version list.** Recommended: fall back to the default version with a note (Requirement 7, criterion 5). Alternative: treat the pin as the Selected_Version for OSV anyway.
17. **GraphQL host. Closed (session 9).** Decision: the host of `GITHUB_GRAPHQL_URL` must equal the host of `GITHUB_API_URL`, otherwise `internal-error` (Requirement 20, criterion 11). This keeps the Token from going to a second host.
18. **Behaviour at the deadline (replaced in session 9).** Recommended: at the deadline every request in flight is aborted, no retry continues, unfinished facts are null, and each source with cancelled or unstarted work is `partial` (Requirement 16, criterion 5; Requirement 17, criteria 3 and 4). If the deadline passes before the Commit_SHA and the manifest selection are known, the route returns `deadline-exceeded` with HTTP 504 (Requirement 21, criterion 6). Alternative: let started Work_Units finish their retries, which gives a longer worst-case time.
19. **GitHub 403 with `Retry-After`. Closed (session 9).** Decision: retry it as a throttle signal (EF-23, Requirement 15, criteria 5, 7 and 8). A 403 without `Retry-After` is final.
20. **Branch in both the URL and the body.** Recommended: equal values are allowed, different values return `invalid-request` with `details.reason` `branch-conflict` (Requirement 21, criterion 4).
21. **Manifest list size.** Recommended: a `manifests` array longer than `DISCOVERY_MAX_MANIFESTS` returns `invalid-request` with reason `too-many-items` (Requirement 21, criterion 3(h)). From `SCAN_MAX_MANIFESTS` + 1 up to `DISCOVERY_MAX_MANIFESTS` distinct paths (11 to 50) returns `too-many-manifests` (Requirement 5, criterion 4).
22. **No-token scans and the Scan_Cache. Closed (session 9).** Decision: a scan without a Token is never stored in the Scan_Cache, because github ends `partial` or `failed` (Requirement 11, criterion 8; Requirement 19, criterion 7).
23. **deps.dev project endpoint (EF-4).** Recommended: it is verified but unused, so it gets no Fixture and no live check (Requirement 23, criterion 13).
24. **Fixture repositories.** The three repositories (npm, Python, Rust) are chosen in the design phase (Requirement 23, criterion 2).
25. **Manifest size unit.** Tree `size` (EF-14) is in bytes and core `MAX_MANIFEST_LENGTH` counts characters (`core/model/constants.ts`, core spec). A byte size above the limit can still parse, so Requirement 5, criterion 8 skips some manifests that core could have parsed. Recommended: keep the conservative skip. Alternative: fetch when `size` is up to 4 times `MAX_MANIFEST_LENGTH` and let core warn.
26. **deps.dev advisory 404 (EF-25).** Recommended: an HTTP 404 on the deps.dev advisory request counts as `ok` (absent), is cached, and leaves the Advisory to the OSV severity rules (Requirement 9, criterion 20). Alternative: count it as not `ok`, which would degrade the depsdev Source_Status for ordinary unknown ids.
27. **Withdrawn `unmaintained` advisories.** Recommended: an advisory with `withdrawn` set does not set `deprecated`, even when its `informational` value is `unmaintained` (Requirement 9, criterion 22). Alternative: any fetched advisory counts, withdrawn or not.
28. **Advisory request set.** Recommended: the deps.dev advisory requests use the same capped id set as the OSV detail requests, sent in parallel with them, so that no advisory waits for the other source (Requirement 9, criterion 20).

29. **Repository names ending in `.git` after removal of one `.git`.** A URL such as `.../x.git.git` parses to the repo `x.git`, and formatting it gives `.../x.git`, which parses to `x`. Round trip and idempotence (Requirement 1, criteria 12 and 13) then fail for such names. Recommended: reject a repository name that still ends in `.git` after removal of one `.git` with `invalid-url` and `details.part` `repository` (GitHub does not allow such names). Alternative: keep the current behaviour and accept that the properties hold only for names that do not end in `.git`. The two properties are restricted to those names until this is decided.
30. **Unreachable manifest cap.** Requirement 5, criterion 6 and the note `manifest-selection-capped` need more than `SCAN_MAX_MANIFESTS` (10) Root_Manifests, but `DISCOVERY_MANIFEST_NAMES` has three names, so a repository has at most three Root_Manifests. The criterion cannot be triggered with the current constants. Recommended: keep it as a defensive rule and test it by injecting a smaller `SCAN_MAX_MANIFESTS` in a unit test. Alternative: remove the criterion and the note code.
31. **Withdrawn informational advisories.** Requirement 9, criterion 6 does not say whether an advisory that is both withdrawn and informational is listed in the `ids` of the `informational-advisory-excluded` note. Recommended: list only non-withdrawn informational advisories, which matches the `unmaintained` rule (OQ 27).
32. **Same-origin redirects.** Requirement 15, criterion 9 handles cross-origin redirects only, and criterion 5 ends any other non-2xx, non-404 status as `failed` after one attempt. GitHub answers a renamed repository on the REST API with a same-origin 301. Recommended: follow same-origin redirects for GET requests up to a new constant `REDIRECT_MAX_HOPS` (3) within one Attempt, without the `Authorization` header leaving the origin. Alternative: treat every 3xx as `failed` with reason category `http-error`.
33. **Scan_Cache hit and the request spelling.** Requirement 19, criterion 6 returns the stored Scan_Result unchanged, but the key uses lowercase owner and repo and omits the branch name, while Requirement 18, criterion 1 sets `repo.owner`, `repo.repo` and `repo.branch` from the request. A hit can therefore return another spelling or another branch name for the same Commit_SHA. Recommended: on a hit, replace `repo.owner`, `repo.repo` and `repo.branch` with the values of the current request and return every other field unchanged. Alternative: add the selected branch name to the key and keep the case-insensitive owner and repo.
